# 项目关键决策记录

本文档记录 MVP 阶段已经确定的关键技术和产品决策。后续如果调整，需要在这里补充新的决策记录，而不是直接覆盖历史判断。

## 决策 1：v0.1 先做单用户模式

### 结论

v0.1 先使用单用户模式，不做完整登录注册流程。

### 具体做法

- 保留 `users` 表，方便后续升级为多用户。
- 系统启动时使用一个默认用户。
- 后端配置中提供 `DEFAULT_USER_ID`。
- 所有资料、切片、会话和消息先归属这个默认用户。
- v0.4 移动端正式接入前，再补完整登录注册和 token 鉴权。

### 原因

第一阶段最重要的是跑通 RAG 闭环。完整认证会增加开发量，但不会直接验证核心价值。

### 影响

- v0.1 可以更快完成笔记问答闭环。
- API 仍然按多用户结构设计，避免后续大改。

## 决策 2：后端先行，Flutter 稍后接入

### 结论

先完成后端 v0.1 的最小 RAG 闭环，再开始 Flutter App。

### 开发顺序

```text
后端 v0.1：笔记 -> 切片 -> embedding -> 检索 -> 回答 -> 引用
  -> 使用 FastAPI Swagger 或极简调试页面验证
后端 v0.2：文件上传和任务状态
  -> Flutter App 开始接入
```

### 原因

移动端体验依赖后端接口稳定。先把资料处理和问答链路跑通，可以避免 App 等后端、后端猜 App。

## 决策 3：LLM 使用 OpenAI-compatible Provider 抽象

### 结论

第一版不把业务代码绑定到某一家模型厂商，而是实现一个 `OpenAI-compatible` 的 provider。

### 配置项

```text
LLM_PROVIDER=openai_compatible
LLM_BASE_URL=
LLM_API_KEY=
LLM_MODEL=
```

### 原因

很多模型服务都兼容 OpenAI 风格接口。这样后续可以切换：

- OpenAI
- DeepSeek
- 通义千问兼容接口
- 智谱兼容接口
- 其他私有模型网关

### 实现要求

- 业务代码只能调用 `LLMProvider` 接口。
- prompt 构建、RAG 上下文、引用来源不能散落在 provider 内部。
- provider 只负责发送请求和返回模型输出。

## 决策 4：Embedding 第一版使用 OpenAI-compatible Provider

### 结论

Embedding 也使用 provider 抽象，第一版默认按 OpenAI embedding 兼容接口实现。

本地开发环境在没有外部 API key 时，可以使用 `local_hash` provider 跑通数据库、切片、向量写入和检索流程。`local_hash` 只用于开发验证，不代表真实语义效果。

### 默认建议

```text
EMBEDDING_PROVIDER=local_hash
EMBEDDING_MODEL=text-embedding-3-small
EMBEDDING_DIMENSIONS=1536
```

接入真实模型时切换为：

```text
EMBEDDING_PROVIDER=openai_compatible
EMBEDDING_API_KEY=<your-api-key>
EMBEDDING_BASE_URL=<provider-base-url>
EMBEDDING_MODEL=text-embedding-3-small
EMBEDDING_DIMENSIONS=1536
```

### 依据

OpenAI 官方 embedding 文档说明，`text-embedding-3-small` 默认向量维度是 1536，`text-embedding-3-large` 默认向量维度是 3072，并且支持通过 `dimensions` 参数调整维度。

参考：[OpenAI Vector embeddings 文档](https://developers.openai.com/api/docs/guides/embeddings)

### 实现要求

- `chunk_embeddings` 表保存 `embedding_model`。
- 同时保存 `embedding_dimensions`。
- 如果后续更换 embedding 模型或维度，需要重建向量索引。
- v0.1 使用 `vector(1536)`。
- 如果后续要支持多种维度并存，再拆分 embedding collection 或增加重建策略。

## 决策 5：v0.1 使用 pgvector 精确检索，后续再加 HNSW 索引优化

### 结论

v0.1 数据量小，先使用 pgvector 的向量相似度查询完成检索闭环。等资料量上来后再添加 HNSW 或 IVFFlat 索引优化。

### 原因

过早优化索引会增加调试成本。MVP 阶段更重要的是检索质量、引用准确性和问答流程。

### 后续触发条件

当单用户 chunk 数量超过 5 万，或查询明显变慢时，开始优化向量索引。

## 决策 6：早期文件存储使用本地存储

### 结论

v0.1 和 v0.2 使用本地文件存储，后续再切换到 S3 / OSS / MinIO。

### 路径建议

```text
backend/storage_data/
```

### 实现要求

- 业务代码通过 `StorageService` 访问文件。
- 不在业务代码中直接拼文件路径。
- `documents.file_path` 保存 storage key，而不是强绑定绝对路径。

## 决策 7：MVP 中文优先

### 结论

MVP 阶段中文优先。

### 具体范围

- App 文案使用中文。
- prompt 使用中文。
- chunk 策略优先适配中文资料。
- 数据库可以保存任意 UTF-8 文本。
- 后续可以扩展英文或多语言。

### 原因

目标用户和当前产品讨论都以中文场景为主，中文优先可以更快打磨体验。

## 决策 8：Flutter 技术栈

### 结论

Flutter App 第一版使用：

```text
状态管理：Riverpod
路由：go_router
网络请求：Dio
Token 存储：flutter_secure_storage
文件选择：file_picker
```

### 原因

这套组合适合资料列表、任务进度、聊天状态和登录态管理，工程复杂度也可控。

## 决策 9：上传接口需要返回 document_id 和 job_id

### 结论

文件上传接口必须返回：

```json
{
  "document_id": "...",
  "job_id": "...",
  "status": "uploaded"
}
```

### 原因

App 上传后要立刻跳转到处理进度页，并通过 `job_id` 轮询任务状态，通过 `document_id` 查询资料详情。

## 决策 10：AI 整理结果可以保存为新笔记

### 结论

整理结果不是一次性内容，必须支持保存为新笔记。

### 原因

这个产品不只是问答工具，还要帮助用户长期沉淀资料。AI 整理结果保存后，可以继续被检索、问答和再次整理。

## 决策 11：本地开发使用 local_hash embedding fallback

### 结论

本地开发默认使用 `local_hash` embedding provider。

### 原因

这样即使没有外部模型 API key，也可以验证：

- chunk 是否生成
- embedding 是否写入 pgvector
- 向量检索 SQL 是否工作
- 创建笔记到检索的闭环是否正常

### 限制

`local_hash` 只提供稳定、可重复的向量，不提供真实语义理解能力。进入问答质量调优前，需要切换到真实 embedding 模型。

## 决策 12：本地开发使用 local_extractive LLM fallback

### 结论

本地开发默认使用 `local_extractive` LLM provider。

### 原因

这样即使没有外部大模型 API key，也可以验证：

- `/chat/query` 接口是否工作
- 检索上下文是否能组装
- 引用来源是否能返回
- 会话和消息是否能保存

### 限制

`local_extractive` 只会根据检索片段生成简单回答，用于开发联调。它不具备真实大模型的总结、推理、联想和生成能力。进入产品体验调优前，需要切换到 `openai_compatible`。

## 决策 13：业务接口使用严格 Bearer 认证

注册、登录和健康检查以外的接口必须携带有效 token。缺少或无效 token 统一返回 `401`，不再回退到默认用户。`DEFAULT_USER_ID` 只保留给本地初始化脚本使用。

## 决策 14：运行时模型设置仅限本地管理员

模型 Provider、Base URL 和 API Key 是服务进程级配置，不属于普通用户个人设置。只有 `RUNTIME_SETTINGS_ADMIN_USER_ID` 可以访问设置接口，且在线写入只允许在本地或开发环境。

## 决策 15：数据库向量维度固定为 1536

当前 `chunk_embeddings.embedding` 和 HNSW 索引使用 `vector(1536)`。切换 embedding 模型时必须保持 1536 维；支持其它维度需要先设计并执行数据库迁移，不能只改运行时配置。

## 决策 16：MVP 后台任务采用数据库恢复机制

上传索引和全量重建仍由应用进程执行，但任务状态持久化到 `jobs` 表。服务启动时会原子领取 pending 任务和超时 running 任务继续执行。进入多机部署阶段后，再迁移到 Redis/Celery 等独立队列。

## 决策 17：媒体解析使用 OpenAI-compatible Provider

图片 OCR 使用支持视觉输入的 `/chat/completions` 兼容接口，音频转写使用 `/audio/transcriptions` 兼容接口。两者使用独立 Provider、模型和密钥配置，默认保持 disabled。

## 决策 18：离线缓存使用加密安全存储

App 缓存当前用户、资料、标签和会话等 GET 响应，网络不可用时自动回退，缓存最长保留 7 天。缓存随退出登录或认证失效清除，避免账号之间共享数据。

## 决策 19：存储后端支持 local 和 S3-compatible

业务代码继续只依赖 storage service。S3 / OSS / MinIO 对象在解析时临时物化为本地文件，因此文本、PDF、OCR 和音频解析无需感知实际存储后端。

## 决策 20：混合检索结果设置最低相关度门槛

向量和关键词结果合并并 rerank 后，低于 `0.35` 的 chunk 不进入回答上下文。没有达到门槛的资料时，问答接口明确返回资料不足，避免仅因为知识库非空就用无关片段生成答案。

## 决策 21：引用 offset 以清洗文本为准

chunk 的 offset 基于 `cleaned_text` 生成，App 打开引用时也优先展示同一字段。PDF 页标记在切片时转为 `page_number`，引用同时返回来源类型、页码或段落，保证显示和定位使用一致的数据。

## 决策 22：运行时 Provider 配置必须可立即使用

管理员把 Provider 设置为 `openai_compatible` 时，后端在写入 `.env` 前校验模型和有效 API Key。不能保存一个下一次请求必然失败的配置，也不能在 Provider 仍启用时清除其密钥。

## 决策 23：显式整理范围不得静默扩大

用户选择标签或具体资料后，如果范围内没有已索引资料，整理接口直接返回明确错误。只有完全未指定范围时，才使用最近 10 份已索引资料作为默认集合，避免空标签意外整理其它私人资料。

## 决策 24：整理结果保存保留来源语义

客户端已经取得整理结果后，通过 `/organize/save-result` 保存原始结果，不重复调用模型。后端统一把资料标记为 `ai_generated`，记录来源资料 ID，并校验这些资料属于当前用户。

## 决策 25：选择器和搜索不能受当前页限制

问答与整理的资料选择器逐页加载全部已索引资料。会话标题搜索由后端在分页前执行，离线缓存同时保留分页总数响应头，避免客户端只处理当前页或在整页边界继续请求未缓存页面。

## 决策 26：相关资料复用混合检索链路

资料详情的“找相关资料”使用当前资料标题、摘要和正文片段作为查询，复用向量、关键词、重排和最低相关度门槛。检索时直接排除当前资料，再按资料 ID 去重，避免自己的 chunk 占满候选结果。

## 决策 27：启动认证临时失败不等于退出登录

只有 `/auth/me` 明确返回 `401` 时才清除 token 和离线缓存。网络故障、后端 `5xx` 或安全存储临时不可用进入独立启动错误状态，允许重试并保留原始深链接，避免瞬时故障破坏有效会话。

## 决策 28：会话范围必须可见、可恢复、可显式清空

聊天请求中的 `scope` 区分“未提供”和“显式空范围”：未提供时可继承历史会话范围，显式空对象表示切换到全部资料。历史详情查询返回保存的范围，App 恢复对应标签、资料和来源类型，并始终展示当前范围摘要。

## 决策 29：列表关联数据必须批量加载

资料列表返回标签时，对当前页所有资料执行一次关联查询并在内存分组，不允许逐资料查询。这样每页无论包含 2 条还是 100 条资料，列表、总数和标签只需要 3 条 SQL。

## 决策 30：多资料整理使用有界且均衡的上下文

一次最多整理 20 份资料。后端用窗口函数在单次查询中限制每份资料的 chunk 数，再把 24,000 字符预算均分给实际有内容的来源，避免大标签范围造成 N+1 查询、模型上下文无限增长或前几份资料挤占全部预算。

## 决策 31：全局 Embedding 配置变化必须重建所有用户索引

Embedding Provider 配置属于服务进程级配置，不属于单个管理员账号。后端比较变更前后的有效索引身份和 OpenAI-compatible 密钥指纹；发生变化时直接创建全用户重建任务，并通过 `X-Embedding-Rebuild-Job-Id` 响应头让 App 跟踪进度。客户端不自行推断配置是否变化，也不额外创建第二个任务。

全用户重建任务使用 PostgreSQL advisory lock 串行执行，任务恢复时保留全用户范围。同一任务如果因服务恢复产生重复执行者，后来的执行者会在取得锁后检查任务终态并退出。这样连续修改配置、服务重启和多实例启动都不会让旧任务在新任务完成后覆盖索引。

## 决策 32：任务恢复使用持续心跳而不是阶段更新时间

解析、Embedding、模型调用和全局锁等待都可能长时间停留在同一阶段，只依赖阶段切换更新 `jobs.updated_at` 会把仍在运行的任务误判为 stale。每个 worker 使用独立数据库会话定期更新运行中任务的时间戳，间隔自动限制在 stale 阈值的三分之一以内；任务进入终态后心跳自动停止。

`GET /health` 只作为不访问依赖的存活检查，`GET /health/ready` 验证数据库、pgvector 扩展和 HNSW 索引并在不可用时返回 `503`。用户通过分页任务历史查看自己的上传和重建记录，管理员发起的全用户任务仍归管理员账号所有，不向普通用户泄露其它账号的任务。

## 决策 33：任务取消采用检查点，重试保留原始历史

任务取消不强制终止解析或外部模型调用。API 把运行任务标记为 `cancel_requested`，worker 在解析、切片、Embedding 提交、富化和逐资料重建边界检查状态；取消发生在向量事务提交前时回滚当前资料，发生在完整索引提交后时保留资料为 `indexed`。服务恢复时直接把遗留取消请求收敛为 `cancelled`，不会重新执行。

只有 `failed` 和 `cancelled` 任务可以重试。重试创建新任务记录并复用原任务类型、资料和权限范围，原记录保持不变；同一资料或同类重建已有活动任务时返回冲突。`success`、`failed`、`cancelled` 记录默认保留 30 天，由启动和周期后台维护按 `JOB_RETENTION_DAYS` 限批清理，兼顾排障历史和数据库增长。

## 决策 34：worker 状态转换必须校验数据库前置状态

任务启动、进度更新、成功和失败不再通过已加载的 ORM 对象直接覆盖状态，而是使用带前置状态条件的原子更新。启动只接受 `pending` 或恢复后的 `running`，进度和成功只接受 `running`，失败只接受 `pending` 或 `running`。

如果取消先提交，后续 worker 更新不会覆盖 `cancel_requested`、`cancelled` 或取消提示，而是进入取消收尾；如果成功或失败先提交，之后的取消请求返回冲突。这样并发结果由数据库中先完成的合法终态转换决定，避免“最后一次普通写入获胜”破坏任务状态机。

## 决策 35：重试任务记录直接来源，原历史清理后允许断链

每次重试创建独立任务，并用 `retry_of_job_id` 指向直接来源任务。连续重试形成可追溯链路，API、任务历史和详情可以明确区分首次执行与重试执行，原任务的状态和错误内容保持不变。

该字段使用可空自引用外键和 `ON DELETE SET NULL`。来源任务达到保留期限被清理时，不级联删除较新的重试任务，而是自动断开引用；客户端只把来源标识作为可选审计信息，不依赖原任务始终存在。

## 决策 36：session-level advisory lock 必须由专用连接持有

全用户索引重建使用 PostgreSQL session-level advisory lock 串行执行，但锁不能绑定到执行资料更新的 ORM `Session`。业务中的 `commit()` 会把连接归还连接池，后续解锁可能取得另一条连接，使原锁永久留在池中。

worker 因此为全局锁单独检出一条连接：获取锁后立即结束隐式事务但保持物理连接占用，任务期间的资料和进度提交使用另一套 Session，最后在同一连接解锁并关闭。获取或释放异常时直接使专用连接失效，确保带锁连接不会回到连接池。

## 决策 37：首次领取和恢复续跑使用不同前置状态

普通后台调度只允许把 `pending` 原子转换为 `running`。服务恢复器先通过行锁领取 `pending` 或 stale `running` 任务并提交为 `running`，随后只有带恢复语义的 worker 才能从 `running` 续跑。

如果服务重启发生在任务创建与原后台线程启动之间，恢复器和原 worker 可能同时到达。此时原 worker 的 `pending` 领取条件失败并抛出专用领取冲突，必须在解析资料、获取全局锁或写入失败状态之前无副作用退出；不能把领取冲突当成业务失败。

## 决策 38：任务执行使用 run token fencing

仅区分 `pending` 和 `running` 仍不足以隔离被判 stale 后恢复的旧 worker。每次首次领取或恢复领取都会生成新的内部 `run_token`；恢复器轮换令牌后，把新令牌随恢复任务传给 worker。

checkpoint、进度、心跳、成功、失败和取消收尾均同时校验任务 ID、`running` 状态和 `run_token`。旧 worker 即使从阻塞调用中恢复，也会在下一次数据库边界得到领取冲突并无副作用退出，不能覆盖新执行者。令牌进入终态时清空，不进入 API 响应，也不作为用户认证凭据。

## 决策 39：任务恢复既在启动执行，也在运行期间周期扫描

只在进程启动时恢复任务会让单个 worker 遗留的 stale running 任务一直等待下一次服务重启。应用因此在启动阶段立即执行一次领取，并通过 lifespan supervisor 按 `JOB_RECOVERY_INTERVAL_SECONDS` 周期重新扫描 pending、cancel requested 和 stale running。

周期扫描复用行锁、`skip_locked` 和 run token fencing，因此多实例可以并行扫描而不会共同执行同一租约。单次扫描失败只记录日志并等待下一周期，不能终止 supervisor；维护清理使用固定批量和跳锁，同样在每轮执行，使超过单批的积压逐步收敛。应用关闭时显式取消并等待 supervisor 退出。

## 决策 40：readiness 必须覆盖后台恢复 supervisor

数据库、pgvector 和 HNSW 正常并不代表任务恢复能力正常。应用在内存中维护线程安全的恢复状态快照，记录最近扫描时间、最近成功时间和连续失败次数；lifespan 同时保留 supervisor task 引用。

`GET /health/ready` 在 supervisor task 已结束或连续扫描失败时返回 `503`，并分别标记 `stopped` 或 `degraded`。下一次扫描成功会清零连续失败并恢复 ready。响应只暴露状态、UTC 时间和计数，不返回数据库异常文本或内部堆栈。

## 决策 41：周期恢复必须有批量背压并跟踪活动 worker

一次领取全部积压任务会同时创建大量 `asyncio.to_thread` 任务，即使线程池本身有上限，事件循环和执行队列仍会无界增长。恢复查询因此按创建时间排序并使用 `JOB_RECOVERY_BATCH_SIZE` 限制每次锁定和派发数量，默认 50、允许范围 1–1000；剩余任务由后续周期继续领取。

恢复状态快照同时记录最近一次派发数量和当前未完成的恢复 worker 数。任务创建后统一增加 active 计数，done callback 无论成功或异常都会递减且不低于 0。readiness 暴露这两个计数，但它们只统计恢复器派发的 worker，不包含正常 API 请求创建的后台任务。

## 决策 42：恢复并发上限必须跨扫描周期生效

单次批量上限不能阻止慢任务跨多个扫描周期累积。恢复 supervisor 因此使用 `JOB_RECOVERY_MAX_ACTIVE_WORKERS` 限制本进程内未完成的恢复 worker，默认 50、允许范围 1–1000。每次扫描先在线程安全状态中原子预留 `min(批量上限, 剩余容量)` 个槽位，再把实际容量作为 SQL `LIMIT`；没有容量时不访问任务表，也不创建新的 `asyncio` task。

数据库认领数量少于预留数量或认领抛出异常时，未使用槽位立即归还；已派发 worker 在 done callback 中归还自己的槽位。该限制约束同一进程内多个扫描周期，不替代 PostgreSQL 行锁和 run token fencing 提供的多实例领取隔离。readiness 同时返回活动 worker 数和配置上限，容量饱和属于正常背压，不会单独把服务标记为 degraded。

## 决策 43：恢复 worker 必须统一注册并限时关闭

只保留启动扫描返回的 task 列表会遗漏周期 supervisor 后续派发的 worker，关闭 lifespan 时也无法判断仍有多少恢复工作正在执行。应用因此为每个进程创建一个恢复 task 注册表，启动扫描和周期扫描都在 task 创建后立即注册，done callback 自动移除；活动 worker 计数仍由恢复状态维护，用于容量控制和 readiness。

关闭顺序固定为先取消并等待 supervisor，阻止新的扫描和派发，再等待注册表中的 worker。等待时间由 `JOB_RECOVERY_SHUTDOWN_TIMEOUT_SECONDS` 配置，默认 30 秒、允许范围 0–3600 秒；超时后取消剩余 asyncio 包装 task，并显式消费 `CancelledError`、归还活动槽位和记录警告。`asyncio.to_thread` 无法强制终止已经运行的线程，因此超时取消是关闭边界和可观测性措施，数据一致性仍由 run token fencing、原子状态转换和进程终止后的 stale recovery 保证。

## 决策 44：同步恢复扫描不得阻塞事件循环

SQLAlchemy 同步会话的维护清理和 `SELECT ... FOR UPDATE SKIP LOCKED` 如果直接从 lifespan 或 supervisor coroutine 调用，会在连接建立、数据库响应或锁等待期间阻塞整个事件循环，使 API、readiness 和关闭信号同时失去响应。两项数据库操作因此通过 `asyncio.to_thread` 执行，调度函数改为异步；容量预留、task 创建和注册仍回到事件循环线程完成。

取消 asyncio 的线程包装任务不能停止已经进入 psycopg 的同步认领，也不能撤销已经提交的 run token。supervisor 在认领等待期间收到取消时，因此使用 shield 保留认领任务并记住关闭请求；数据库调用返回后，先为所有已认领租约创建并注册恢复 worker，再传播 `CancelledError`。这样关闭可能多等待一次有限的认领查询，但不会制造已经变成 `running` 却没有对应 worker 的任务；之后由 lifespan 的 worker 关闭超时统一收敛。

## 决策 45：恢复 readiness 必须同时检查扫描耗时和结果 freshness

supervisor task 仍处于 pending 只能证明 coroutine 没有退出，不能证明它仍按周期完成扫描。同步数据库调用移入线程后，连接或查询长期挂起也不会再阻塞 readiness 请求，因此必须显式记录当前扫描开始时间和最近一次完成耗时。状态使用 UTC 时间用于响应展示、使用 monotonic clock 计算耗时，避免系统时钟调整产生负耗时。

当前扫描超过 `JOB_RECOVERY_SCAN_STALE_AFTER_SECONDS` 时立即标记 `scan_overdue`，默认阈值 30 秒、允许范围 1–3600 秒；没有超时扫描但最近成功时间超过 `max(3 × JOB_RECOVERY_INTERVAL_SECONDS, 2 × 扫描超时阈值)` 时标记 `success_stale`。readiness 还稳定区分 `supervisor_stopped`、`state_unavailable`、`scan_failed` 和 `never_succeeded`。这些原因只描述恢复能力，不包含数据库异常文本；扫描超时只改变 readiness，不强制取消无法安全中断的同步认领。

## 决策 46：恢复 SQL 必须使用事务级 statement timeout

扫描耗时监控能让流量入口停止向异常实例发请求，但不能释放在 PostgreSQL 中长期等待的恢复线程。启动及周期维护和任务认领因此在各自事务开始时调用 `set_config('statement_timeout', 毫秒值, true)`，超时由 `JOB_RECOVERY_STATEMENT_TIMEOUT_SECONDS` 配置，默认 30 秒、允许范围 0.1–3600 秒。查询被 PostgreSQL 取消后事务回滚，周期 supervisor 记录失败并在下一周期重试。

第三个 `true` 参数把设置限制在当前事务；提交、回滚和 statement timeout 导致的事务中止都会恢复连接原值，连接归还池后不会影响 API 查询、worker 心跳或其它请求。使用 `set_config` 参数绑定而不是拼接 `SET` 字符串，避免把配置值直接插入 SQL。该超时覆盖任务 SELECT、取消收尾查询、清理 DELETE 和提交前的相关语句，但不替代连接建立和连接池等待超时。

## 决策 47：数据库连接建立和连接池等待必须有显式上限

PostgreSQL `statement_timeout` 只有在连接已经取得且事务语句开始执行后才生效，无法约束网络握手或 QueuePool checkout。应用 engine 因此通过统一 `create_database_engine()` 配置 psycopg `connect_timeout` 和 SQLAlchemy `pool_timeout`，分别由 `DATABASE_CONNECT_TIMEOUT_SECONDS`（默认 5 秒、范围 1–60）与 `DATABASE_POOL_TIMEOUT_SECONDS`（默认 10 秒、范围 0.1–300）控制。

这两个上限覆盖 API Session、后台 worker、任务恢复和全局重建 advisory-lock 专用连接；Alembic 保持独立 engine 配置，避免运行时连接池参数改变迁移行为。`pool_pre_ping` 继续用于丢弃失效的池连接。readiness 返回连接、池等待和恢复 statement timeout 三层配置，但数据库异常响应仍不包含 URL、凭据、主机或驱动错误文本。

## 决策 48：health 数据库查询使用独立 statement timeout

连接和池等待成功后，`SELECT 1`、pgvector 扩展检查或 HNSW 目录查询仍可能在 PostgreSQL 内等待。readiness 和 capabilities 的 HNSW 状态查询因此在事务第一条语句设置 `DATABASE_HEALTH_STATEMENT_TIMEOUT_SECONDS`，默认 2 秒、允许范围 0.1–30 秒；它独立于恢复 SQL 的 30 秒上限，保证健康检查快速失败，不因后台任务允许较长查询而长期占用 FastAPI 线程。

超时仍使用事务级参数化 `set_config`，Session 关闭时自动回滚并恢复连接设置。readiness 捕获连接、设置超时或查询任一阶段的异常，统一返回 `503`、`database=unavailable`、`vector/index=unknown`；capabilities 无法确认索引时返回 `hnsw_index=unknown`。两条响应都不包含数据库 URL、主机、凭据或原始异常文本。

## 决策 49：连接池容量必须显式配置并可观测

只配置 checkout timeout 无法区分 PostgreSQL 不可用和应用连接池已经耗尽。运行时 QueuePool 因此显式使用 `DATABASE_POOL_SIZE` 与 `DATABASE_POOL_MAX_OVERFLOW`，默认分别为 5 和 10、允许范围分别为 1–100 和 0–100；总容量固定为两者之和，不依赖 SQLAlchemy 隐式默认值。

readiness 在 checkout 前读取 QueuePool 的 checked-in、checked-out 和 overflow，计算当前容量利用率。SQLAlchemy 在基础池尚未填满时会返回负 overflow，该内部值对外统一规范为 0。checked-out 达到总容量时直接返回 `503` 和 `database=pool_saturated`，不再等待 `DATABASE_POOL_TIMEOUT_SECONDS`；否则执行正常依赖查询。该快照反映探针尝试 checkout 前的瞬时状态，不能替代持续时序指标，但足以区分池耗尽和数据库查询失败。

## 决策 50：所有运行时连接必须有默认 statement timeout

仅为 health 和恢复事务设置超时仍会让普通 API 查询、worker 状态更新或直接使用 engine 的 advisory lock 无限等待。统一 engine 因此通过 psycopg 连接参数 `options=-c statement_timeout=毫秒值` 设置会话默认值，由 `DATABASE_STATEMENT_TIMEOUT_SECONDS` 配置，默认 30 秒、允许范围 0.1–3600 秒。该值从连接建立起生效，包括首次 pre-ping 之后的所有 ORM 与 Core 语句。

health 与恢复路径继续使用事务级 `set_config(..., true)` 覆盖为各自上限；事务提交或回滚后恢复连接级默认值。这样普通查询有统一保护，health 可以更快失败，恢复扫描也可以按需要使用不同预算。运行时 engine 的默认值覆盖 Session、后台 worker 和 advisory-lock 专用连接，但不影响 Alembic 的独立迁移 engine；readiness 返回全局、health 和恢复三类 SQL timeout，便于确认有效配置。

## 决策 51：数据库瞬时故障必须返回稳定且可重试的 503

连接失败和 statement timeout 由 SQLAlchemy 表现为 `OperationalError`，QueuePool checkout 超时表现为 SQLAlchemy `TimeoutError`。如果它们落入通用异常处理器，客户端只能得到不可区分的 `500`，也无法判断是否适合重试。FastAPI 因此为两类异常注册专用处理器，统一返回 `503` 和相同的 `message/detail`，通过 `DATABASE_RETRY_AFTER_SECONDS` 控制 `Retry-After`，默认 5 秒、范围 1–300。

处理器不把原始异常、SQL、绑定参数、连接 URL、主机或凭据放入响应；警告日志只记录请求方法、路径和异常类型，也不记录异常字符串或 traceback 中的 SQL 参数。Flutter 已从稳定 JSON 的 `message` 字段提取用户提示，无需对写请求自动重试；是否重试由具体交互和幂等语义决定。约束冲突等非瞬时数据库错误不映射为 503，仍由业务层转换或通用错误处理器处理。

## 决策 52：Flutter 只对可缓存 GET 的 503 使用离线回退

数据库瞬时故障已经使用明确的 `503`，此时资料、标签、会话、当前用户和运行时设置等只读页面仍可展示七天内的加密缓存。Dio 拦截器因此把网络错误与 `503` 都视为缓存回退候选，但必须同时满足请求方法为 GET 且 `ApiCache` 白名单、键和有效期校验通过；无缓存时继续抛出后端稳定错误。

缓存响应保持状态码 200 和原有分页响应头，并在 `extra` 中标记 `from_cache=true` 与 `cache_fallback_reason=offline/service_unavailable`；503 的 `Retry-After` 同时保留为元数据。POST、PATCH、DELETE 等写请求绝不读取缓存、不清除现有缓存，也不伪装成功，避免用户误认为修改已经提交。401 仍优先清除 token 和全部缓存，不允许回退到旧账号数据。

## 决策 53：缓存回退必须在全局界面明确提示来源

仅在 Dio `Response.extra` 标记缓存来源不足以让用户知道当前内容可能不是实时数据。Dio 命中缓存后因此发布全局 `CacheFallbackNotice`：网络故障标记为 `offline`，后端 503 标记为 `serviceUnavailable` 并保留 `Retry-After`。通知对象每次命中都重新创建，连续相同原因也能触发界面反馈。

根 `MaterialApp` 使用全局 `ScaffoldMessenger` 显示浮动 SnackBar。离线时提示“正在显示离线缓存”，503 时提示“服务暂不可用，正在显示缓存”，并使用对应的网络状态图标；新通知先替换当前提示，不排队堆叠。该提示覆盖登录恢复、主导航和详情页，不改变页面数据模型，也不把写请求错误转换为通知或成功状态。

## 决策 54：缓存来源提示必须持续显示并标明数据时间

短时 SnackBar 可能在用户开始阅读页面前消失，也无法回答“当前缓存有多旧”。加密缓存条目因此把原有 `cached_at` 解析为 UTC 时间，并与数据、分页响应头一起通过 `CachedApiResponse` 原子返回；Dio 的缓存响应在 `extra.cached_at` 和全局 `CacheFallbackNotice.cachedAt` 中传递同一时间，避免分别读取缓存数据和元数据产生不一致。

根 `ScaffoldMessenger` 改用持续 `MaterialBanner`：离线与服务不可用继续使用不同文案和图标，次级文本按本地时区显示缓存更新时间，同日使用 `HH:mm`、跨日使用 `MM-dd HH:mm`。新缓存通知立即替换当前横幅而不排队；实时 GET 成功、成功写入、401 或 GET 错误无可用缓存时把通知状态置空并隐藏横幅。失败的写请求仍保持失败，也不会误报数据已经恢复实时。

## 决策 55：缓存横幅通过独立 readiness 探针主动确认恢复

持续横幅如果只能等待页面自然产生下一次 GET，在用户停留阅读缓存内容时无法及时确认服务已经恢复；`MaterialBanner` 也不应使用无语义的占位 action。横幅因此提供“重新连接”操作，探测期间固定显示“连接中”和进度图标、禁用重复点击，结束后恢复可操作状态。

恢复探针使用独立且不带业务缓存拦截器的 Dio 请求 `/health/ready`，避免探针自身从缓存回退后以 200 响应伪装为后端已恢复。只有 HTTP 200 且响应 `status=ready` 时才清除全局缓存通知；503、断网、超时、异常 JSON 或其它失败都保持原横幅和缓存时间。控制器复用同一个进行中的 Future，程序化重复调用也只发送一次请求；探针不携带 token、不读取或写入业务缓存，也不自动重放任何写请求。

## 决策 56：readiness 恢复后必须重验证页面数据再隐藏缓存提示

readiness 只证明后端依赖此刻可用，不能证明屏幕上由 Riverpod 保存的缓存响应已经更新；探针成功后直接隐藏横幅会让用户把旧页面误认为实时数据。因此决策 55 中“ready 即清除通知”的收尾被重验证阶段取代：探针成功只递增全局缓存重验证代次，资料、标签、会话、运行时设置和当前用户 API provider 都依赖该代次并重新请求。当前用户采用静默刷新，不把已登录页面重定向到 loading 路由。

恢复控制器在重验证期间继续保持“连接中”并去重调用。只有真实业务 GET 成功后，原 Dio 拦截器才清除缓存通知；如果重验证再次回退缓存，横幅保留并更新来源。10 秒内没有实时响应时控制器只结束加载状态、重新启用按钮，不清除通知。没有缓存可用的其它失败 GET 也不得清除已有横幅，因为它不能证明用户当前看到的缓存内容已经更新；401 和成功写请求仍按会话与数据失效规则清除全部缓存状态。

## 决策 57：缓存重验证必须按代次汇总全部活动请求

用第一条成功 GET 结束重验证仍存在并发顺序竞争：首页、资料页或整理页可能同时加载资料、标签、会话和当前用户，其中一条实时响应先清除横幅，另一条随后回退缓存，界面会短暂甚至最终错误地显示为实时。缓存通知和重验证状态因此从 Dio 客户端抽离为共享状态模块，每次 readiness 恢复创建单调递增的 generation；白名单 GET 在请求开始时把该代次写入内部 `RequestOptions.extra`，并在实时成功、缓存回退或失败时对同一代次结算一次。

批次记录注册请求数、活动请求数以及实时、回退、失败结果。活动数归零后保留 100 毫秒注册窗口，吸收同一轮 Riverpod 失效产生的相邻请求；只有注册数大于零、全部请求均为实时成功且没有回退或失败时才清除横幅。任意部分回退、无缓存失败、没有实际重取请求或 10 秒总超时都只结束“连接中”状态并保留警告。旧代次的晚到响应被忽略，401、成功写请求和会话失效会取消当前批次，保证响应完成顺序不改变最终缓存来源提示。

## 决策 58：加密缓存索引更新与会话清理必须串行

每个缓存响应先写独立安全存储条目，再通过读改写维护索引。多个 GET 并发完成时，如果两次写入同时读取旧索引，最后一次索引写会覆盖另一条新增键；数据条目仍存在却无法被 `clear()` 枚举，注销或 401 清理后可能留下旧账号缓存。`ApiCache` 因此不再是不可变常量对象，而是在单实例内用 Future 队列串行执行缓存读取、条目写入、索引读改写和清理。先调用的写入必须在后调用的 clear 之前完整结束，clear 返回后不存在本轮并发写产生的孤立条目。

缓存键与索引升级为 `api_cache_v2_*` 命名空间，使旧版本可能已经遗留但未进入索引的 v1 条目不再可读。清理流程同时读取 `api_cache_v2_index` 和旧 `api_cache_index`，删除两个索引仍能枚举的条目；无法枚举的历史孤立键保留为不可访问数据，避免使用全安全存储 `deleteAll` 误删登录凭据之外的其它机密。缓存失败仍不得使业务请求失败，512 KiB 单条上限和七天有效期保持不变。

## 决策 59：缓存键必须使用不可逆的授权会话作用域

索引串行化可以阻止新的孤立条目，但安全存储自身仍可能在注销、401 或切换账号时暂时删除失败。如果缓存键只包含 API 路径和查询，新 token 对相同请求会命中旧账号条目，形成跨账号数据泄露。Dio 已在网络发送前把 `Authorization` 写入 `RequestOptions`，缓存键因此加入完整授权头的 SHA-256 指纹；相同路径和参数只有在同一 token 下才能读写同一条目。键中不保存原始 token，也不使用可逆 Base64 作为会话标识；无授权请求进入独立 `anonymous` 作用域。

缓存命名空间同步升级为 `api_cache_v3_*`，使没有会话作用域的 v2 条目和可能遗留的 v1 条目都不再参与读取。`clear()` 依次处理 v3、v2 和 v1 索引中仍可枚举的键；即使删除完全失败，旧 token 的 v3 条目也无法由新 token 命中。token 轮换会自然失效旧缓存，这是为账号隔离接受的可用性取舍；单条大小、有效期、响应头保存和并发操作队列保持不变。

## 决策 60：加密缓存必须同时限制条目数和正文总字节数

七天有效期只阻止读取旧数据，不会自动释放安全存储；分页、搜索词和详情 ID 都进入缓存键，长期使用会持续增加条目并最终耗尽 Web localStorage 或原生安全存储配额，使后续缓存写静默失败。v3 索引因此从键列表升级为版本化元数据，逐条记录键、UTC 缓存时间和 JSON 正文的 UTF-8 字节数。默认最多保留 64 条且正文合计不超过 4 MiB，单条 512 KiB 上限继续生效；每次写入先清理超过七天的条目，再按缓存时间从旧到新淘汰，直到两个边界都满足。

读取发现条目过期、JSON 损坏或正文已经缺失时，同时删除正文和索引元数据。现有 v3 键列表会在下一次写入时读取正文补齐时间与字节数，并迁移为元数据格式，无需再次更换缓存命名空间；v1/v2 清理兼容继续保留。清理索引时只接受与该索引版本匹配的缓存键前缀，即使索引损坏或被篡改也不能借机删除 `access_token` 等非缓存安全存储项。容量限制可在测试中注入更小值，生产 provider 始终使用默认边界。

## 决策 61：安全存储缓存操作不得无限阻塞业务请求

Dio 在实时 GET 响应返回前等待缓存写入，在网络错误回退前等待缓存读取，认证和成功写请求还会等待缓存清理；如果平台安全存储插件挂起，单次非关键缓存操作会让业务响应和后续串行队列一起长期失去进展。`ApiCache` 的公开读、写、响应头写入和 clear 因此统一使用 2 秒调用预算，预算包含队列等待与实际插件调用。写入或清理超时继续按成功的业务响应处理，读取超时按无缓存处理，原始异常与超时都不泄露到用户界面。

Future 的 `timeout` 不能取消已经进入平台插件的调用，因此超时只结束当前调用者的等待，不提前释放内部串行队列。底层操作完成后仍按调用顺序继续：先发起但已超时的写必须在后发起的 clear 之前收敛，不能为降低延迟重新引入索引和会话清理竞争。若插件永久不返回，后续缓存调用也会在各自预算后降级，不影响网络与内存会话；跨账号安全仍由 v3 token 指纹隔离保证。操作预算可在测试中缩短，生产 provider 使用固定默认值。

## 决策 62：登录凭据安全存储也必须有有限等待边界

缓存操作有超时并不能保护 token 路径：启动和每个 Dio 请求读取 token，登录与注册保存 token，401 与注销删除 token；任一插件 Future 永久挂起都会让认证状态停在 loading 或无法退出。`TokenStorage` 因此统一为 read、write 和 delete 设置 2 秒预算并继续抛出超时或平台异常，由调用场景决定状态转换。Dio 和启动认证保留外层 2 秒防线，覆盖测试替身或未来绕过默认实现的情况。

登录或注册只有在清理旧缓存且新 token 持久化成功后才设置 `AuthState.user`；保存超时进入明确错误状态，不能把仅存在内存的认证响应当成可恢复登录。注销继续用 `finally` 清空内存用户，即使 token 删除或缓存清理超时也立即退出界面会话；底层 delete Future 可能稍后完成。401 路径同样先尝试限时删除，但无论本机存储结果如何都会触发内存会话失效。测试预算可缩短，生产默认固定 2 秒。

## 决策 63：token 保存超时必须回滚晚到写入

Future 超时不取消平台写入，登录界面报告“保存失败”后，原 write 仍可能晚到并把 token 留在设备上，导致下次启动意外恢复一个用户认为失败的会话。`TokenStorage` 因此像缓存一样串行执行 read、write 和 delete；保存抛出超时或平台异常时，立即在原 write 之后排入补偿操作。补偿先读取当前 token，只有它仍等于该次失败保存的值才删除，避免删除其它来源已经写入的新凭据。

后续登录保存和显式注销按调用顺序进入同一队列。失败 write、条件补偿、新 write 的顺序保证旧登录的回滚先于新登录落盘；如果另一个 token 已经成为当前值，旧补偿无副作用退出。补偿自身不阻塞已经返回错误的界面 Future，也不设置新的外部超时；平台调用恢复后继续收敛。永久挂起时内存认证仍保持未登录，缓存由 token 指纹隔离；测试覆盖单次晚到写入删除和失败后紧接成功保存两种顺序。

## 决策 64：部署环境必须在启动时拒绝不安全的 JWT 配置

HS256 的签名安全取决于所有 API、worker 和管理脚本共享的 `AUTH_SECRET_KEY`。如果生产部署沿用仓库默认值、示例占位值或过短密钥，攻击者可以离线猜测密钥并自行签发任意用户 token。`Settings` 因此在模块导入时统一校验认证配置：只有大小写不敏感的 `local` 和 `test` 环境允许开发密钥，其它环境必须使用不在已知占位列表中且至少包含 32 个 UTF-8 字节的密钥；空白密钥在所有环境都被拒绝。校验失败直接阻止进程启动，不让不安全实例进入 readiness 或接收流量。

访问 token 有效期继续由 `ACCESS_TOKEN_EXPIRE_MINUTES` 配置，默认 10080 分钟（7 天），但限制在 1–43200 分钟（30 天），防止错误配置生成即时失效或近乎永久的凭据。JWT 解码保持 PyJWT 的 `exp` 强制校验，过期 token 在数据库用户查询之前统一转换为 `401`。仓库示例保留仅供本地复制的占位密钥并明确部署前生成随机值；密钥轮换会使既有 token 立即失效，当前版本尚未引入 refresh token 或平滑双密钥轮换。

## 决策 65：登录失败限制必须跨实例共享且不持久化原始标识

单进程内存计数器会在服务重启时清空，并且多实例之间不能共享，攻击者可以轮换实例绕过限制。登录失败状态因此存入 PostgreSQL 的 `auth_login_attempts` 表，以账号和 ASGI 客户端地址两个独立作用域计数。每个作用域键使用 `AUTH_SECRET_KEY` 对“作用域类型 + 规范化值”执行 HMAC-SHA256，数据库只保存 64 字符摘要、计数、窗口和阻止时间，不保存原始邮箱或 IP；密钥轮换后旧摘要不可再命中，并由保留期清理。

默认策略是在 900 秒窗口内允许同一账号 5 次、同一客户端 20 次失败，第 5 次账号失败或第 20 次客户端失败立即返回统一 `429`，通过 `Retry-After` 指示剩余阻止秒数。窗口、阻止时间、两个阈值和状态保留期均可配置；保留期必须至少覆盖窗口与阻止时间。每次失败使用数据库时间，并通过 PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` 在行锁下原子递增，多个 API 进程或并发请求不会丢计数。旧状态在失败写入时按 `updated_at` 索引顺带清理，避免表无限保留历史作用域。

登录检查同时查询两个作用域，任一仍被阻止就不再查询用户或执行密码哈希。普通失败无论邮箱是否存在都返回“邮箱或密码错误”；不存在的邮箱仍对固定虚拟哈希执行一次 PBKDF2，缩小账号枚举的时序差异。成功登录只删除账号作用域，不能通过一个有效账号清空同客户端对其它账号的失败记录。密码正文限制为 1–1024 字符，注册仍保留至少 6 字符要求，避免超大输入放大 PBKDF2 成本。

客户端作用域使用 ASGI 已解析的 `request.client.host`，应用不直接解析或信任 `X-Forwarded-For`。反向代理部署必须在 Uvicorn 层把 `FORWARDED_ALLOW_IPS` 限制为实际代理地址；错误地信任任意来源会允许伪造客户端地址并削弱该作用域。账号作用域不依赖代理配置，仍然跨实例生效。当前方案允许攻击者通过 5 次失败暂时阻止已知账号，这是账号级暴力破解保护的可用性取舍；统一响应和 HMAC 状态不泄露该账号是否真实存在。

## 决策 66：密码哈希必须自描述并在成功登录时渐进升级

旧格式 `pbkdf2_sha256$salt$digest` 隐含固定的 210,000 次 PBKDF2-HMAC-SHA256，字符串本身没有迭代次数。直接提高代码常量会让全部旧密码无法验证，继续固定常量又无法随硬件和安全建议演进。新密码因此改用 `argon2-cffi` 的 Argon2id，自描述字符串包含算法版本、内存、时间和并行参数；当前固定为 `m=19456 KiB, t=2, p=1`，哈希与 salt 分别为 32 和 16 字节。应用不开放环境变量降低这些成本，所有实例使用同一最低基线。

验证器按格式分派：`$argon2id$` 使用库实现验证并通过 `check_needs_rehash` 比较当前策略；历史三段式 PBKDF2 只按原 210,000 次算法验证；未知、截断、非十六进制或摘要长度错误的格式统一验证失败。新注册、本地默认用户脚本和未知账号的固定虚拟哈希都使用 Argon2id。历史 PBKDF2 密码仍可正常登录，但永远标记为需要升级；错误密码绝不改写数据库。

正确密码验证后，应用先在 ORM 用户对象写入新的 Argon2id 哈希，再删除账号维度的登录失败状态，最后用同一个数据库事务提交；只有提交成功后才向客户端返回 JWT。这样数据库失败不会把仅在内存中升级的登录当成成功，也不会出现限流状态已清除但密码哈希未落库的部分结果。当前 Argon2 参数未来变化时，相同路径会为成功登录的旧参数用户再次升级，无需批量接触明文密码或强制全员重置。旧哈希只会随活跃用户登录逐步消失，长期不登录账号仍保留兼容验证能力。

## 决策 67：注册重复必须以数据库唯一约束作为最终裁决

注册前查询邮箱可以让普通重复请求跳过 Argon2 计算并快速返回，但不能保证并发正确性：两个 API 线程或不同实例可能同时查询到不存在，各自完成哈希后再竞争插入。`users.email` 的 `uq_users_email` 唯一约束因此是最终一致性边界，服务层在 `commit()` 捕获 SQLAlchemy `IntegrityError` 后必须先回滚当前 Session，再读取 psycopg 的 `orig.diag.constraint_name`。

只有诊断名称精确等于 `uq_users_email` 时才转换为 `EmailAlreadyRegisteredError`，由路由返回稳定 `409` 和“邮箱已注册”。缺少约束名或命中其它约束的完整性错误在回滚后继续原样抛出，由通用故障路径处理，避免数据库 schema 缺陷、字段约束错误或未来新增约束被误报成业务重复。已存在邮箱的预检查和提交竞态使用同一领域异常与响应，不向客户端暴露 SQL、驱动诊断、约束名称或密码哈希。

失败的唯一键事务不能继续用于查询或刷新，因此回滚发生在领域异常抛出之前；冲突请求不会签发 JWT，也不会调用 `refresh()`。成功请求仍提交并刷新唯一的用户记录。真实并发验证用屏障强制两个请求都通过预检查后才继续哈希和插入，结果必须严格为一个 `201`、一个 `409` 且数据库只有一个用户，以证明覆盖的是实际竞态而不是顺序执行的快速路径。

## 决策 68：注册额度必须在密码哈希前跨实例原子消费

登录失败限流不能约束攻击者持续使用随机邮箱调用注册；每个新邮箱都会执行 Argon2 并可能创建用户，既能放大 CPU/内存消耗，也会无界增加账号数据。注册因此增加独立的 `registration-client` HMAC 作用域，继续使用 PostgreSQL `auth_login_attempts` 状态表和原子 upsert。表名保留是为了兼容已经运行和迁移到决策 65 的实例；共享存储层已抽离为通用认证限流实现，登录与注册只提供各自的作用域和阈值语义。

默认每个 ASGI 客户端地址在 3600 秒窗口内允许 5 个通过 Pydantic 请求体验证的注册请求。每个请求在查询用户、检查重复邮箱和执行 Argon2 前先原子消费一次；内部阻止阈值设为“允许数 + 1”，因此前 5 次继续业务，第 6 次设置 3600 秒阻止时间并立即返回统一 `429` 与 `Retry-After`。多个进程同时消费同一摘要时由行级冲突更新串行计数，真实 6 路并发必须得到恰好 5 个允许和 1 个阻止。缺失 ASGI 客户端地址时使用共享 `unknown` 作用域，避免异常部署静默失去保护。

额度事务在业务注册前独立提交：重复邮箱、唯一键竞态或后续数据库失败仍消耗这次已接受请求，成功注册也不清空客户端额度，攻击者不能用有效注册重置计数。请求体本身未通过校验的 `422` 不进入路由，因此不写数据库。客户端摘要继续由 `AUTH_SECRET_KEY` 执行 HMAC-SHA256，不保存原始 IP；窗口、阻止时间、允许数和保留期均可配置，保留期必须覆盖窗口与阻止时间。

客户端地址仍以 ASGI `request.client.host` 为准，并依赖 Uvicorn 正确限制可信代理。该边界可以控制单一来源的账号创建和 Argon2 成本，但分布式来源仍可分别取得额度；生产开放注册后仍应按产品需求引入邮箱所有权验证、邀请机制、验证码或边缘网关风控，而不能把单维度限流当成完整反滥用系统。

## 决策 69：访问 token 必须绑定可撤销的数据库会话

仅验证 HS256 签名和 `exp` 的 token 在签发后七天内无法由服务端单独撤销；客户端“退出登录”过去只删除本机安全存储，复制或泄露的 token 仍可继续访问。每次注册和登录因此创建独立 `auth_sessions` 记录，以随机 UUID 主键作为 JWT `jti`。新 token 同时强制包含 `sub`、`jti`、`iat`、`exp`、`iss`、`aud` 和 `token_type=access`；解码固定验证算法、签名、签发方、受众、时间和类型，默认只允许 30 秒时钟偏差。签发时刻规范到 UTC 整秒，使 JWT NumericDate 与数据库 `expires_at` 完全一致。

认证依赖先严格解码 JWT，再按 `jti` 查询会话，要求会话存在、`user_id` 与 `sub` 相同、数据库到期时间仍有效，最后确认用户存在。任何一步失败都返回相同 `401`，不区分 token、会话或用户原因。旧版只有 `sub/exp` 的 token 缺少必需声明和对应会话，升级后统一失效并要求重新登录；这是从不可撤销 token 切换到服务端会话的一次性兼容边界，不保留可绕过会话检查的旧解码路径。

注册时用户 flush、首个会话插入和最终提交位于同一事务；唯一邮箱冲突可在 flush 阶段捕获并回滚，既不留下用户也不留下会话。登录时旧密码重哈希、账号限流清理和新会话插入同事务提交，JWT 即使提前在内存编码也只有提交成功后才返回。签发会话前使用 `SELECT ... FOR UPDATE` 锁定用户行，清理全局过期会话，并只保留该用户最新 9 个既有会话再添加新会话，因此默认最多 10 个且并发登录不能越界；上限允许配置为 1–100。

`POST /auth/logout` 通过已经认证的 `jti + user_id` 删除当前会话并提交，随后相同 JWT 即使签名和 `exp` 有效也会因会话缺失返回 `401`；其它设备的会话不受影响。删除而不是永久保存 revoked 标记，使显式注销不会累积历史行；自然过期行在下一次签发时按 `expires_at` 索引清理，用户删除则由外键级联清理。

Flutter 必须在删除本机 token 前调用服务端 logout，否则请求拦截器无法再携带当前凭据。远端调用使用 2 秒预算，成功、401、断网、超时或其它失败后都继续清理本地 token、加密缓存和内存用户，保持“退出按钮一定结束当前设备会话”的既有可用性。离线退出无法撤销可能已经外泄的服务端会话，这是网络不可达时不可消除的边界；当前版本没有 refresh token、设备管理页或离线撤销队列。

## 决策 70：改密必须撤销全部旧会话并为当前设备原子换发 token

只更新 `users.password_hash` 不会影响已经签发的数据库会话，泄露 token 仍可使用到期。`POST /auth/change-password` 因此要求已认证会话和当前密码，先用 `SELECT ... FOR UPDATE` 锁定用户，再检查登录限流、验证当前哈希和禁止复用相同明文密码。当前密码错误与登录共用账号和客户端失败计数，第 5 次按现有策略返回 `429 + Retry-After`；成功验证清除账号失败状态。

改密成功路径在同一事务中写入当前 Argon2id 哈希、删除该用户全部 `auth_sessions`、创建一个新的当前设备会话并提交。响应使用完整 `AuthResponse` 返回替换 token；提交前编码的 JWT 不会在事务失败时暴露。这样其它设备和改密请求自身携带的旧 token 都立即失效，只有替换 token 可继续访问。真实双旧会话验证必须得到两个旧 token `401`、替换 token `200`，数据库密码只能通过新密码验证。

Flutter 收到成功响应后必须先清理账号缓存并把替换 token 写入安全存储，再确认当前用户状态。若后端已改密但替换 token 保存超时或失败，旧本地 token 已不可恢复，App 清理本机凭据和缓存、结束内存会话并明确要求重新登录；不能继续显示已登录用户。API 校验失败或网络失败发生在后端成功响应之前时，App 保留当前用户和旧 token，并在改密对话框显示错误。

`POST /auth/logout-all` 删除用户全部会话且不签发替代 token。Flutter 对这项明确的安全命令采用不同于普通退出的失败策略：只有服务端确认 `204` 或明确 `401` 后才清理本机状态；网络或服务错误保留当前会话并提示重试，不能把未完成的全局撤销伪装成成功。成功后当前和其它设备 token 全部返回 `401`。当前版本尚未提供会话列表、设备名称或选择性远程设备撤销。

## 决策 71：设备会话管理只保存平台名称并按用户隔离撤销

仅有当前设备退出和全设备退出时，用户无法判断账号在哪些设备保持登录，也不能只处理某一个可疑会话。`auth_sessions` 因此增加可空的 `client_name VARCHAR(128)`；注册、登录和改密换发 token 时从 `X-Client-Name` 写入。后端折叠首尾与连续空白并截断到 128 个字符，缺失或纯空白保存为 `NULL`。Flutter 只按运行目标发送 `Personal AI Web/Android/iOS/Windows/macOS/Linux` 等产品平台名，不发送 IP、User-Agent、硬件 ID 或持久设备指纹。该字段用于帮助用户辨认客户端类别，不作为可信身份或风控信号；升级前的会话继续有效并显示为未知设备。

`GET /auth/sessions` 使用认证依赖提供的 `user_id + current jti`，只查询该用户 `expires_at > now` 的记录，按创建时间和 ID 倒序返回 `id/client_name/created_at/expires_at/is_current`。当前标记完全由数据库会话 ID 与已验证 JWT 的 `jti` 比较，不接受客户端传入。列表不主动删除自然过期行；它们已有到期索引并会在下一次签发时统一清理，读取路径只排除过期结果。

`DELETE /auth/sessions/{session_id}` 在同一删除语句中同时约束会话 ID 和当前用户 ID。目标不存在或属于其它用户时都返回相同 `404`，不能通过响应判断另一个账号是否持有某个会话；成功删除并提交后，目标 JWT 下一次认证立即返回 `401`，发起请求的其它会话保持有效。API 允许撤销本人任一会话，Flutter 设备管理对话框则把当前会话显示为明确状态而不提供该删除按钮，当前设备退出继续走语义更清楚且具备本机清理流程的 `POST /auth/logout`。

Flutter 使用 `FutureProvider.autoDispose` 实时加载设备列表，展示本地化登录时间和有效期；其它设备使用带 tooltip 的退出图标，删除期间固定按钮尺寸显示进度，成功后使 Provider 失效并从服务端重载，读取或删除失败均保留明确的错误与重试状态。`/auth/sessions` 不加入加密离线缓存白名单，因为过期的设备安全状态比离线不可用更危险。真实双账号、双设备验证要求当前设备标记唯一、跨账号删除为 `404`、选择性删除为 `204`、目标 token 为 `401`、当前 token 仍为 `200`，并在验证后清理临时用户、会话与注册限流记录。

## 决策 72：公开注册必须由部署策略控制且客户端不得内置开发凭据

注册限流只能限制单一客户端来源的创建频率，不能表达一个部署是否应允许陌生人创建账号。个人或团队私有部署通常只需要预先创建的账号；如果生产实例沿用始终开放的注册路由，任何能访问 API 的来源仍可在各自额度内持续增加账号。`AUTH_REGISTRATION_ENABLED` 因此使用可空配置：显式 `true/false` 直接生效；未设置时只在大小写和空白规范化后的 `local/test` 环境开放，其它环境默认关闭。该默认值不依赖 Flutter 构建模式，最终策略只由后端运行环境决定。

`GET /auth/config` 是无需认证的最小能力响应，只返回最终 `registration_enabled` 布尔值并设置 `Cache-Control: no-store`。它不返回 `APP_ENV`、密钥、token 参数、限流阈值或任何用户信息。`POST /auth/register` 在路由进入共享额度消费、用户查询和 Argon2 之前检查同一最终策略；关闭时统一返回 `403` 与“当前不开放新账号注册”。请求体仍由 FastAPI 正常校验，但有效请求不会创建限流记录、数据库用户或会话。关闭注册不影响登录、改密和现有会话。

Flutter 登录页移除 `local@example.com/123456` 预填值，邮箱和密码初始为空，只通过系统 autofill hints 接受用户主动保存的凭据。登录页异步读取 `authConfigProvider`：只有明确得到开放状态才显示注册入口；查询失败时保留邮箱、密码和登录按钮，只保守隐藏注册。直接访问 `/register` 不能绕过该展示策略，页面在加载时显示进度，关闭时只提供返回登录，查询失败时提供重试；即使客户端状态过期或被篡改，后端 `403` 仍是最终边界。

真实验证必须覆盖 local 未显式配置时能力为 `true` 且注册 `201`，production 使用强密钥但未显式配置时能力为 `false` 且注册 `403`，两种能力响应都不包含其它认证字段。显式配置允许部署者覆盖默认值，但生产开放注册仍需要按产品风险继续增加邮箱所有权验证、邀请制、验证码或网关策略，本开关不替代这些控制。

## 决策 73：生产开放注册默认使用一次性 HMAC 邀请码

注册开关解决“是否允许创建账号”，但生产显式开启后仍会回到任何来源都能在限流额度内注册的状态。当前项目没有邮件发送 Provider，邮箱验证码无法形成可部署闭环；邀请码可以由部署管理员通过现有数据库连接安全生成，因此先增加一次性邀请模式。`AUTH_REGISTRATION_INVITE_REQUIRED` 同样采用可空配置：显式值直接生效，未设置时 `local/test=false`、其它环境 `true`。公开能力响应扩展为 `registration_enabled + invitation_required`；注册关闭时后者返回有效值 `false`，避免客户端展示不可执行的邀请表单。生产无邀请公开注册必须同时显式设置注册开启和邀请关闭，不能因只打开一个开关意外暴露。

`auth_registration_invites` 只保存随机 UUID、64 字符 `code_hash`、`expires_at`、`used_at` 和创建时间。管理脚本使用 `secrets.token_urlsafe(32)` 生成约 256 位随机原码并只输出一次；摘要为以 `AUTH_SECRET_KEY` 作为密钥的 HMAC-SHA256，数据库泄露不会直接暴露可注册凭据，代码首尾空白在摘要前统一删除且大小写保持敏感。轮换认证密钥会有意使所有未使用邀请码失效，管理员必须在轮换后重新生成。脚本默认 168 小时有效期，只接受正整数小时；邀请码创建量由可信管理员控制，因此不把它纳入面向不可信请求的自动保留清理。

邀请模式的注册仍先消费 PostgreSQL 共享客户端额度，使攻击者不能无限尝试邀请码。随后按 HMAC 摘要执行 `SELECT ... FOR UPDATE`，缺失、未知、已使用和到期统一抛出同一领域错误并映射为 `403`，不泄露邀请码状态。有效行保持锁直到用户 flush、首个 `auth_session` 插入、`used_at` 写入和事务提交全部完成；邮箱唯一键或其它完整性错误会回滚整笔事务，不能消耗邀请码却不创建账号。两个进程并发提交同一码时，后取得行锁的请求必须看到已提交的 `used_at` 并失败，因此严格只有一个 `201`。

Flutter 只在能力明确要求时显示“邀请码”字段，禁用自动纠错和建议，提交前去除首尾空白；空值在本地阻止，服务端仍是最终裁决。真实验证必须用生成脚本创建原码，以两个同步请求和不同邮箱并发注册，得到严格 `201 + 403`，再次复用为 `403`，数据库只有一个用户且 `used_at` 非空；最后清理用户、级联会话、邀请码和注册限流记录。local 默认模式还必须证明 `invitation_required=false` 且无邀请码注册保持 `201`，避免安全增强破坏开发闭环。

## 决策 74：注册邀请码管理只向固定管理员开放且原码只返回一次

部署管理员需要了解现有邀请码状态并主动终止尚未使用的凭据，单独依赖数据库脚本无法形成完整的日常管理闭环。因此在认证命名空间增加管理员列表、创建和撤销接口，授权边界与运行时模型设置一致：只有 `RUNTIME_SETTINGS_ADMIN_USER_ID` 对应的已认证用户可访问，其他用户对三类操作统一返回 `403`。列表支持分页和 `active/used/expired/revoked` 状态筛选，创建有效期限制为 1–8760 小时；列表与创建响应都设置 `Cache-Control: no-store`。

表结构增加可空 `revoked_at`，状态优先级固定为已使用、已撤销、已过期、可使用。撤销使用行锁读取：有效邀请码首次撤销写入数据库并返回 `204`，重复撤销幂等返回 `204`，已使用或已过期返回 `409`，不存在返回 `404`。注册校验把 `revoked_at` 与缺失、未知、已使用和到期放入同一个 `403` 错误边界，不能通过注册响应探测邀请码的具体状态。

创建 API 是唯一返回原始 `code` 的 HTTP 响应；分页列表永远不返回 `code` 或 `code_hash`，数据库仍只保存 HMAC 摘要。Flutter 仅在当前用户的 `is_admin=true` 时展示“我的 > 注册邀请码”，管理页提供分页、状态筛选、创建、一次性原码复制和有效邀请码撤销；界面隐藏不是授权边界，所有操作仍由后端管理员校验裁决。

真实强制邀请验证要求管理员创建返回 `201`，普通用户列表、创建和撤销均为 `403`，有效邀请码首次和重复撤销均为 `204`，撤销筛选可查询到该记录，使用撤销原码注册返回 `403`，且列表不包含原码或摘要。验证完成后必须清理临时用户、会话、邀请码和注册限流记录。

## 决策 75：Flutter 用户界面不得直接渲染异常对象

后端稳定 JSON 错误并不能自动保证客户端安全：Dio 的 `toString()` 会拼接连接类型、URL、XMLHttpRequest 诊断和底层异常，安全存储、文件选择器、语音插件及普通 Dart 异常也可能包含平台实现细节。Flutter 因此禁止把异常对象、`error.toString()`、`DioException.message` 或字符串插值后的原始错误直接放入页面、状态文案和 SnackBar。

统一映射函数只从 Dio 响应 JSON 中读取非空字符串类型的 `message`，缺失时兼容读取 `detail`。这两项由自有后端的异常边界生成，可以保留邀请码无效、资料仍在处理或权限不足等可行动的业务信息。空白、数组式校验详情、非 JSON 响应和没有响应的传输错误均不可信，调用方必须提供“暂时无法加载资料”“保存失败，请稍后重试”等与操作对应的固定兜底；认证 token 保存、聊天、上传、整理、任务操作和语音识别遵循同一规则。

任务记录的 `error_message` 不属于客户端异常对象，而是后端 worker 为用户持久化的处理失败原因，因此继续按业务数据展示。测试必须覆盖结构化 `message/detail` 保留、连接与未知异常隐藏、认证存储超时不泄露类型名，以及至少一个包含多个异步数据源的页面错误态；静态扫描还应保证生产 Flutter 代码不再出现直接异常渲染模式。

## 决策 76：认证启动初始化与交互操作加载状态必须分离

认证控制器原先用同一个 `loading` 同时表示启动会话恢复和登录、注册、改密等用户操作，路由又把所有 `loading` 都重定向到 `/loading`。因此用户点击提交后表单会立即卸载；一旦请求失败，重新创建的页面已经丢失邮箱、昵称、密码和确认密码，错误恢复成本远高于一次普通校验失败。

`AuthState` 增加独立的 `initializing`：控制器构造和显式 `loadCurrentUser()` 时同时设置 `loading=true, initializing=true`，只允许这类启动恢复触发全屏加载路由。登录、注册、改密、当前设备退出和全设备退出继续使用 `loading` 表示操作进行中，但保持 `initializing=false`；页面据此禁用重复提交控件，路由不得离开当前表单。操作结束后两种状态都必须按各自语义复位，不能根据通用 `loading` 推断启动阶段。

回归测试必须覆盖启动认证仍保留深链接、交互登录失败后邮箱和密码仍在原页面、密码框获得焦点并全选，以及交互注册失败后昵称、邮箱、密码和确认密码全部保留。这样启动阶段仍有明确的全屏等待体验，而可恢复的业务失败不会破坏用户已经输入的上下文。

## 决策 77：用户业务数据必须引用真实用户且禁止直接级联删除

资料、切片、向量、会话、消息、任务和标签表早于正式多用户认证建立，虽然应用服务始终按 `user_id` 过滤，它们的数据库列原先没有引用 `users.id`。应用错误、运维脚本或不完整的测试清理因此可以写入不存在的用户 ID；用户记录被删除后也可能留下无法再通过正常 API 访问和清理的孤儿业务数据。应用层隔离不能替代数据库对所有者存在性的最终约束。

迁移 `0017_user_owner_fks` 为 `documents`、`document_chunks`、`chunk_embeddings`、`conversations`、`messages`、`jobs` 和 `tags` 增加已验证的用户外键，模型元数据同步声明相同约束。迁移不自动删除、重新归属或猜测历史孤儿记录；任何孤儿都会使约束创建失败并让 PostgreSQL 事务回滚，部署者必须先核对其业务归属。测试枚举全部含 `user_id` 的模型表，未来新增此类表但没有外键时必须失败。

业务外键使用 `ON DELETE RESTRICT`，因为删除数据库用户还必须协调对象存储文件、等待中或运行中的任务以及其它外部副作用，不能用数据库级联把未完成的账号删除伪装成成功。`auth_sessions` 是唯一保留 `ON DELETE CASCADE` 的用户从属表；会话只用于撤销凭据，不持有外部资源，用户最终被受控删除时应同时失效。后续账号删除接口必须先设计可重试的文件清理和任务 fencing，再按明确顺序删除业务记录与用户；本决策只建立所有权完整性，不宣称已经支持账号删除。

## 决策 78：对象存储删除必须通过事务 outbox 持久化并可重试

数据库事务不能覆盖本地文件系统或 S3：先删除文件再提交资料删除，一旦数据库提交失败会留下仍可查询但原文件已消失的资料；先提交数据库再直接调用存储，进程崩溃或网络错误又会留下没有业务行可供重试的孤立对象。在数据库事务内等待远端删除同样不能获得原子性，只会延长行锁和连接占用。因此资料删除不再直接调用存储后端，而是在删除资料行的同一事务写入 `storage_deletions` outbox；事务回滚时两者都保留，提交后即使进程立即退出，文件清理意图仍然存在。

每条任务保存入队时的存储后端、不含凭据的存储位置快照、对象 key、尝试次数、下次重试时间以及有限期 `lease_token`。本地位置快照是解析后的根目录，S3 快照只包含 endpoint、region、bucket 与 SSL 模式，不保存 access key 或 secret。多个实例使用 `FOR UPDATE SKIP LOCKED` 领取到期且未被有效租约占用的行，领取时原子增加尝试次数并写入新 token；完成和失败更新都必须匹配同一 token，过期 worker 不能删除或覆盖已经被重新领取的任务。实际删除成功后才移除 outbox 行；失败只保存异常类型、释放租约并按 30 秒起步、最多 1 小时的指数退避安排下次尝试。进程在外部调用完成而数据库确认前崩溃时，对象删除会在租约到期后重复执行，因此本地缺失文件和 S3 `DeleteObject` 都必须按成功处理。

队列在执行前把 `storage_backend + storage_scope` 与当前部署配置比较；类型、local 根目录、S3 endpoint、region、bucket 或 SSL 模式任一变化时都保留任务并报告 `StorageBackendChangedError`，不能把旧 key 解释到新的存储命名空间。启动时立即调度一个批次，运行期间按固定间隔或路由 wakeup 继续扫描；同一进程只允许一个 worker，跨进程由数据库租约协调。关闭时先停止 supervisor，再限时等待已派发 worker，超时取消 asyncio 包装任务，底层线程若未完成则依靠租约过期恢复。readiness 暴露最近批次时间、领取/完成/失败数量、连续异常和 freshness；supervisor 停止、批次异常、处理超时、成功过旧或仍有删除失败都会返回稳定的降级原因。

`DELETE /documents/{id}` 的 `204` 语义改为“业务资料已删除且物理文件删除任务已持久接收”，而不是保证响应前对象已经消失。路由仍触发即时批次以缩短常见路径延迟，周期 supervisor 是崩溃和临时故障后的最终收敛机制。上传尚未建立资料行时的空文件和创建前失败仍可直接清理临时对象；一旦文件 key 已进入持久业务数据，所有删除必须经过 outbox。

## 决策 79：自助删除账号必须校验当前密码并在单一事务中移除全部业务身份

仅删除 `users` 行会被业务外键阻止，简单改成级联又会绕过对象存储和运行任务；只在 Flutter 隐藏入口也不能构成安全边界。因此普通用户通过 `DELETE /auth/account` 提交 `current_password` 和固定 `confirmation=DELETE`。当前密码验证与登录、改密复用 PostgreSQL 账号和客户端限流：错误密码记录失败并返回 `400`，不触发全局 `401` 清理；达到阈值返回 `429 + Retry-After`。固定 `RUNTIME_SETTINGS_ADMIN_USER_ID` 返回 `409`，部署者必须先迁移管理员配置，避免删除唯一管理入口后无法管理模型设置和邀请码。

服务先用 `FOR UPDATE` 锁定用户，再检查切片与资料、向量与切片、消息与会话、任务与资料、标签与资料的所有者是否一致；任何跨账号关联都返回稳定 `409`，不能通过级联误删另一用户的数据。随后按 job ID 和 document ID 固定顺序锁定该用户的任务与资料，把去重后的文件 key 写入 `storage_deletions`，再依次删除向量、切片、消息、任务、会话、资料和标签，最后删除用户并提交。用户外键阻止并发请求在用户删除提交后写入新业务行；已经持有旧 `run_token` 的 worker 在 job 行删除后无法再通过条件更新或写入已删除资料，形成账号删除的最终 fencing。

数据库提交后，用户和全部 `auth_sessions` 已消失，当前与其它设备 token 下一次请求都必须返回 `401`。`204` 表示账号业务身份已永久删除且文件删除意图已持久接收，物理对象仍由 outbox wakeup 和周期 supervisor 收敛；本版本不提供软删除、恢复窗口或管理员代删。Flutter 只向非管理员展示红色危险入口，要求当前密码和明确勾选；远端失败保留当前用户、输入和本机 token，远端成功后即使安全存储清理失败也必须结束内存会话，因为旧 token 已不可能恢复有效。

真实验收必须先为临时普通用户创建两个会话、文件资料与任务、笔记切片与向量、标签、会话和消息；错误密码删除为 `400` 且当前 token 仍为 `200`，正确密码删除为 `204`，随后用户及八类从属表计数全部为 0、两个旧 token 都为 `401`、outbox 与物理文件最终消失。管理员使用正确密码删除必须为 `409` 且会话继续有效。验收后清理临时限流摘要和任何残留 outbox、文件或会话。

## 决策 80：文件资料必须持久化上传时的存储来源

对象 key 只在所属存储命名空间内有意义。同一个 `documents/example.pdf` 在两个本地根目录、S3 bucket 或 endpoint 下可以指向完全不同的对象；如果资料行只保存 key，稍后删除时从当前 `STORAGE_BACKEND` 和位置反推来源，配置切换会把旧 key 解释到新命名空间并可能误删无关文件。outbox 在入队时记录当前配置只能保护入队后的变化，不能恢复上传到入队之间已经丢失的历史来源。

`documents` 因此为每条文件资料持久化上传成功时的 `storage_backend` 和不含凭据的 `storage_scope`，格式与 outbox 相同：local 保存解析后的绝对根目录，S3 保存 endpoint、region、bucket 和 SSL 模式。数据库检查约束要求 `file_path + storage_backend + storage_scope` 要么全部为空、要么全部非空，使笔记与文件资料边界不可处于半完成状态。单资料删除必须使用资料自身快照入队；账号删除按 `backend + scope + key` 去重，不能把不同命名空间中的相同 key 合并。任何文件资料缺少来源时都停止删除并返回稳定 `409`，保留业务行供人工核对，不能静默猜测。

迁移 `0019_document_storage` 无法从旧表仅有的 key 推导历史命名空间，只能用执行迁移时的部署配置回填现有文件资料，再创建约束。因此升级前必须保证该配置仍指向全部历史文件的真实位置；若历史文件已经分布在多个命名空间，部署者必须先按实际来源修正数据。迁移不会移动对象，也不会在后续配置变化时改写资料快照。

outbox worker 继续把任务快照与当前配置严格比较。配置不同会保留任务、记录 `StorageBackendChangedError` 并让 readiness 以 `deletion_failed` 降级；恢复原配置且退避到期后才执行删除。真实验收覆盖上传保存原 scope、在另一 local 根目录下删除资料仍生成原 scope 任务、worker 返回 failed 且原文件存在，以及恢复原根目录后任务完成、文件和 outbox 最终消失。

## 决策 81：文件解析必须在读取前校验上传时的存储来源

决策 80 让删除链路不再猜测文件位置，但异步解析仍曾直接按当前配置物化 `file_path`。上传和 worker 执行之间可能发生部署切换；如果新旧 local 根目录或 S3 命名空间中存在相同 key，worker 不只是会找不到旧文件，还可能把另一个对象的内容写入当前资料的 `raw_text`、切片和向量索引。这会破坏资料完整性，并可能把不属于该资料的内容带入后续检索与回答。

存储抽象因此提供按预期 backend 和 scope 物化文件的受控入口，文件解析必须同时提交资料行中的 `file_path`、`storage_backend` 和 `storage_scope`。入口先复用 outbox 删除的同一配置一致性检查，完全匹配后才调用 local 或 S3 读取；来源字段缺失直接失败，类型、根目录、endpoint、region、bucket 或 SSL 模式任一不同都抛出稳定 `StorageBackendChangedError`，提示恢复原存储配置后重试。笔记没有物理文件，继续直接使用数据库正文，不进入该检查。

当前版本不持久化 S3 凭据，也不在配置切换后根据历史 scope 自动连接旧存储。自动访问旧位置会绕过当前部署授权边界，本地绝对路径也不能代表仍获批准的读取范围；因此配置不匹配时正确行为是停止。document worker 按既有失败路径把资料和 job 置为 `failed`，不创建 chunk 或 embedding；管理员恢复原配置后，用户可通过现有任务重试接口创建带 lineage 的新任务。

真实验收必须在两个 local 根目录放置同一 key 但不同正文，并让资料保存原根目录快照。带 run token 的 worker 在错误根目录下执行时，资料和 job 必须失败、`raw_text` 保持为空且 chunk/embedding 都为 0；恢复原根目录后的重试必须只索引原正文，并保留 `retry_of_job_id`。验收结束后删除临时账号、任务、索引、outbox 和两个文件。

## 决策 82：存储一致性审计必须只读并按 provenance 隔离命名空间

事务 outbox 可以让已知删除最终收敛，但不能自动解释上线前遗留对象、人工复制、数据库手工修改或存储侧丢失。只比较 key 字符串也不够：相同 key 在不同 backend 或 scope 中代表不同对象，把历史 scope 的资料引用用于当前根目录或 bucket 会掩盖真正的 orphan，甚至把另一个命名空间的对象误认为仍被使用。因此提供独立 CLI 审计当前部署配置，不把大规模对象枚举放进 readiness 或普通 API 请求。

审计先固定当前 `storage_backend + storage_scope`，只查询来源完全匹配的文件资料和 `storage_deletions`。资料 key 必须逐一检查实际存在性；待删除 key 即使对象已经不存在也不是错误，因为删除具有幂等语义，且 inventory 中仍存在的待删除对象不能算 orphan。local inventory 只递归当前根目录的 `documents/` 并拒绝逃逸根目录的 key；S3 inventory 使用分页列表且只覆盖当前 `S3_KEY_PREFIX`。当前 scope 中位于历史 S3 前缀的资料仍通过逐 key 存在性检查验证，但审计不会枚举和宣称能发现所有历史前缀中的孤立对象。

输出把 missing document、orphan、invalid document key 和 invalid pending-deletion key 分开，并使用排序后的稳定 JSON。全部为空时返回 `consistent` 和进程退出码 0，任一非空时返回 `drift` 和退出码 1，便于人工或运维任务检测。命令刻意不提供 `--delete`、自动修复或数据库改写；orphan 可能来自尚未提交资料行的并发上传，missing 也可能是存储暂时不可用，未经业务核对不能把一次审计结果直接转成破坏性操作。

真实验收在当前 local scope、无文件资料和空 outbox 的基线上运行，只读 inventory 必须准确报告已有的一个历史孤立文件，missing 与 invalid 都为 0、退出码为 1，并确认文件内容、时间和数据库计数没有变化。S3 通过分页 fake 覆盖 prefix、bucket、存在与 404 语义；local 测试还要求审计不存在的根目录时不得创建目录。

## 决策 83：孤立对象处置必须精确复核并通过持久 outbox

只读审计刻意不能自动删除，但完全依赖人工直接调用文件系统或 S3 CLI 会绕过已经建立的 provenance guard、持久重试和 readiness 可观测性。另一方面，提供“删除全部 orphan”会把跨系统非原子快照中的瞬时上传、共享 bucket 中的非本应用对象或错误配置一次性转成不可恢复损失。因此处置使用独立命令，只接受一个完整 key，不解析 glob、不读取批量清单，也不把审计命令本身增加删除选项。

命令默认再次运行当前 backend/scope 的完整审计并只返回 `action=none`。key 必须精确出现在当次 `orphan_keys` 中；资料引用、当前 scope 的 pending outbox、inventory 不存在、非法路径或其它 scope 的同名对象都不能通过。只有操作员额外提供 `--enqueue` 时，服务才在同一数据库 Session 中重新审计、添加带当前 backend/scope 快照的 `storage_deletions` 行并提交。它不在 CLI 进程中调用存储删除，提交失败不会触碰对象，进程退出或后端离线也不会丢失已经提交的意图。

后续物理删除完全沿用 outbox supervisor：配置已经变化时拒绝错误命名空间，临时 S3 或文件系统失败按退避重试，成功后才移除任务。CLI 无法制造数据库与对象存储的原子快照，并发上传在文件落地和资料行提交之间仍可能短暂呈现 orphan；应用生成 UUID key 使正常上传复用既有精确 key 的概率可忽略，但人工导入或共享命名空间仍要求在低写入时段逐 key 复核。当前版本不把一次审计结果升级为自动清理授权。

真实安全验收只能运行 dry-run：已有历史 orphan 必须返回 `orphan/action=none/0`，不存在 key 返回 `not_orphan/action=none/1`，两次调用后文件哈希不变且 outbox 仍为 0。入队服务通过 fake Session 验证成功路径严格先执行幂等 insert 后 commit，非孤立和已有 pending 的 key 在任何数据库写入前拒绝；实际旧文件除非获得明确运维授权，不在研发验收中 enqueue。

## 决策 84：相同存储位置的删除意图必须在数据库级幂等

对象删除本身具备幂等语义，但重复 outbox 行并非无害：文档删除与账号删除竞态、两个孤立对象处置命令或多个 API 实例可以同时通过应用层检查。重复行会分别领取租约、增加 S3 调用、独立退避，并在同一个外部故障上重复让 readiness 降级。先查询再插入仍有经典竞态，进程内锁也不能覆盖多实例，因此删除意图的身份必须由数据库约束为 `storage_backend + storage_scope + storage_key`。

迁移 `0020_storage_deletion_unique` 在创建唯一约束前删除语义等价的历史重复行，按 `created_at + id` 保留每组最早记录。保留行继续携带自身尝试次数、租约和下次重试时间；迁移不会合并错误文本或猜测不同 scope 是否等价。部署必须先排空旧 worker，避免迁移删除仍由旧进程持有的重复租约；物理删除仍然幂等，即使旧 worker 在停机边界已经完成外部调用也不会造成错误对象删除。

所有入队统一改用 PostgreSQL `INSERT ... ON CONFLICT ON CONSTRAINT ... DO NOTHING RETURNING id`，不在 service 内 commit，继续服从资料、账号或孤立对象处置的外层事务。`RETURNING` 有结果表示本事务创建新意图，无结果表示相同任务已经存在；不能依赖驱动 `rowcount`，因为 psycopg 在真实 `ON CONFLICT` 执行中可能对已成功插入也返回不可用于布尔判断的值。并发冲突不得更新已有行，否则会覆盖其 lease token、attempts 或退避安排。

真实迁移验收在 `0019` 下插入两条同位置任务，升级后必须只保留创建时间最早的固定 ID并存在命名唯一约束。顺序和双线程同时入队都必须得到恰好一个 `True`、一个 `False` 且数据库只有一行；验收任务随后精确清理，outbox 恢复为空。孤立对象 CLI 在极窄的“审计后、插入前”竞态中通过该返回值报告 `already_queued`，而不是误报创建了第二条任务。

## 决策 85：删除队列 readiness 必须以共享数据库状态补强进程内批次状态

`StorageDeletionState` 只能记住单个进程最近一次批次。失败任务写入 `last_error` 并进入未来退避后，如果实例重启，启动批次会因 `next_attempt_at` 未到而领取 0 条，新状态看起来完全成功；另一实例也可能从未领取过该失败行。反方向同样存在：实例 A 记住一次失败，实例 B 后来成功删除并移除共享行，A 若只保留本地 `last_failed` 会永久误报降级。readiness 不能用任一进程的局部历史代表持久队列整体健康。

health 因此在已经取得的数据库 Session 和同一 `DATABASE_HEALTH_STATEMENT_TIMEOUT_SECONDS` 事务中执行一次聚合，不增加第二次连接池 checkout。响应暴露 pending 总数、`last_error` 非空的 failed 数、有效 lease 数、当前 eligible 数、最早创建/下次尝试时间，以及 abandoned 数。abandoned 定义为 `attempts > 0`、没有 `last_error` 且租约为空或已过期，表示 worker 已经领取但没有可靠记录完成或失败；它与正常 `attempts=0` 新任务和仍持有有效 lease 的首次处理明确区分。

任一持久 failed 行让所有实例以 `persistent_deletion_failed` 返回 `503`；任一 abandoned 行以 `abandoned_deletion_lease` 返回 `503`。本地批次异常、超时、supervisor 停止和 freshness 规则继续保留。本地 `last_failed` 只在共享队列仍有任务时作为补充信号；全局队列已经由其它实例清空后，旧局部失败不会阻止恢复。数据库不可用或池饱和时不尝试伪造共享快照，相关字段返回 `null`，整体状态已经由数据库原因降级。

真实重启验收写入一条 `last_error` 非空且下次尝试在未来的任务：新实例启动批次 claimed/failed 均为 0，但 readiness 必须通过数据库看到 pending/failed 各 1 并返回 `503 persistent_deletion_failed`。随后替换为 attempts 为 1、无错误、无 lease 的未来任务，必须返回 `503 abandoned_deletion_lease`；精确清理后下一次探针立即恢复 `200/ready`，不等待本地 supervisor 周期，outbox 最终为 0。

## 决策 86：失败删除任务的人工重试只能重排资格，不能绕过 worker

指数退避最大可达一小时。操作员恢复原存储配置或修复 S3 权限后，如果只能等待 `next_attempt_at`，readiness 会在已知问题消失后继续长时间降级；再次 enqueue 又会被决策 84 的唯一约束正确忽略。直接从 CLI 删除对象会绕过 lease token、配置快照、批量上限和完成 fencing，也无法在外部删除成功而数据库确认失败时可靠恢复。因此人工操作只能把既有任务重新变为 eligible，物理副作用仍由统一 worker 执行。

独立 CLI 默认按当前 backend/scope 和一个完整 key 检查状态，不解析 glob 或批量清单。状态区分未来退避的 `failed_backoff`、没有错误记录的 `abandoned_backoff`、已经到期的 `eligible`、有效租约 `active_lease`、lease token/到期时间不成对的 `invalid_lease`、首次未尝试 `not_attempted`、`not_found` 和 `invalid_key`。只有 failed/abandoned backoff 可进入写路径；eligible 已可由 supervisor 领取，无需制造无意义更新，其它状态需要等待或人工修复而不能强行夺取。

显式 `--retry` 使用 `SELECT ... FOR UPDATE` 锁定目标行并读取数据库时间，把 `next_attempt_at` 更新为 now，清除已经失效的 lease token/期限，但保留 attempts 和 `last_error` 供审计与 readiness 使用。service 不自行 commit，由 CLI 外层事务提交；提交后仍要等待运行中的 supervisor 下一扫描周期。命令不直接调用 batch processor，因为批处理可能同时领取其它 eligible 任务，也不跨进程调用内存 wakeup。

真实验收创建一个受控 local 文件和 attempts=2、带错误类型、未来一天重试的 outbox 行。dry-run 必须返回 `failed_backoff/action=none`；显式重试后 attempts 与错误不变、时间已到且状态为 scheduled。随后统一 worker 必须 claimed/completed 各 1、failed 0，文件和 outbox 最终消失。单元测试覆盖 failed 与 abandoned 重排、有效 lease、新任务、eligible、非法 key 和不完整 lease 均不被错误修改。

## 决策 87：后台任务持久错误必须经过显式公开边界

通用 API 异常处理会隐藏未捕获异常，但 worker 把错误写入 `jobs.error_message`、`documents.error_message` 和 `metadata.enrichment_error` 后，这些字段会作为正常业务响应返回 Flutter。直接持久化 `str(exc)` 会绕过 HTTP 错误边界；pypdf/FileNotFoundError 可以包含绝对存储路径，httpx 和对象存储异常可能包含 URL、bucket、请求诊断或响应正文，数据库异常还可能包含 SQL 与约束信息。客户端把任务错误当成业务数据并不等于任意后端异常天然适合公开。

后端建立 `PublicJobError` 标记和统一消息函数。只有代码审查过的公开错误类型允许原文进入数据库，当前包括解析器主动生成的固定提示、空文本/空切片等业务失败，以及不含凭据的存储配置变化提示。其它异常只根据 worker 当前阶段映射为固定文案：文本读取、PDF、OCR、音频转写、内容处理、切片、Embedding、单资料重建和顶层重建各有稳定兜底。公开消息限制长度；异常对象、cause、traceback 和原始响应只写服务端日志。

解析服务在存储 provenance guard 之后包裹第三方库和 Provider 调用，保留 `StorageBackendChangedError` 与自身 `DocumentParsingError`，把其它异常按 source type 转换。document worker 计算一次公开消息并同时写 document 与 job，不能出现两个端点暴露不同细节。embedding rebuild 的逐资料错误和最终汇总只能拼接用户自己的资料标题与公开文案；enrichment provider 统一转换为固定 `EnrichmentProviderError`，记录 metadata 时再次执行公开映射，未来调用者不能绕过。

真实验收创建一个数据库引用存在但 local PDF 文件缺失的带 token 任务。服务端日志必须保留底层 `FileNotFoundError` 和绝对路径用于诊断，但数据库 document/job 只能保存“PDF 解析失败，请确认文件完整且格式有效”。临时用户通过真实登录后读取 `/jobs/{id}` 和 `/documents/{id}` 都得到相同稳定错误，响应中不得出现 `storage_data`、用户目录、异常类型或 errno。验收后通过账号删除和 outbox 清理临时用户、会话、任务与资料。单元测试还覆盖内部 URL、`api_key` 字样和 `provider down` 均不进入持久字段。

## 决策 88：API 路由只公开命名业务异常

全局异常处理会把未捕获异常转换为稳定 `500`，但路由曾在较大的 `try` 区块中捕获内置 `ValueError`、`LookupError` 和 `PermissionError`，再把 `str(exc)` 写入 HTTP detail。这些内置类型并不是公开契约：例如模型设置路由的区块同时包含 `.env` 文件读写，文件系统 `PermissionError` 可以携带绝对路径；相关资料检索中的 Provider `ValueError` 可能包含配置名、URL 或响应诊断。路由捕获它们会绕过全局边界，并把内部故障误分类成用户错误。

认证、模型设置、相关资料和邀请码管理服务因此为可公开分支定义命名异常，路由只捕获这些明确类型。异常类继续继承原内置类型，保留服务层兼容性，但意外的同类异常不再匹配路由。模型设置校验使用固定公开文案，不回显未支持的 provider 原值；未知文件系统和 Provider 异常由全局 handler 记录 traceback 并返回“服务器内部错误”。相关资料不存在保持 `404`，已存在但尚未完成索引属于当前状态冲突，修正为 `409`。

ASGI 回归测试向登录、相关资料和模型设置路径注入包含绝对路径、内部 URL、`api_key` 与 provider trace 的普通内置异常，响应必须是稳定 `500` 且不含注入文本；命名异常仍分别得到既定 `400/401/403/404/409`。路由目录扫描不得再出现对内置 `ValueError`、`LookupError` 或 `PermissionError` 的直接捕获。

## 决策 89：422 校验响应不能回显原始请求值

FastAPI 的 `RequestValidationError.errors()` 默认包含触发错误的 `input`。对于超长密码、无效邀请码、访问令牌和模型 Provider API Key，这会把完整敏感值复制到 `422` 响应；响应可能再被反向代理、客户端网络日志、崩溃报告或调试工具记录。输入来自请求者并不意味着应该在响应链路中重复传播，特别是凭据长度校验本身最容易触发这一行为。

统一 validation handler 继续返回顶层 `message` 和结构化 `detail`，但每条错误只从 Pydantic 结果读取 `type` 和 `loc`，并生成公开 `msg`。原始 `input`、可能携带异常对象的 `ctx`、Pydantic 错误文档 URL 及未来新增扩展字段全部丢弃。Flutter 只读取顶层字符串 `message`，不会依赖 detail 中的输入副本，因此这一收紧不改变客户端错误展示或业务 schema。

改动前真实 `/auth/login` 请求提交带唯一标记的 1100 字符密码，`422` 正文长度为 1340，明确包含标记和 `input` 字段。回归测试同时覆盖手工构造的 password、异常 ctx、内部 URL，以及经过 ASGI/Pydantic 产生的 password 和 api_key 长度错误；响应必须只包含白名单字段且不出现任一敏感标记。重启验收使用同一真实请求，要求状态仍为 `422`，但标记、`input`、`ctx` 均不存在。

## 决策 90：422 的公开消息按错误类型稳定本地化

完成输入脱敏后，真实超长密码请求的顶层消息仍是 Pydantic 生成的 `String should have at most 1024 characters`。Flutter 优先显示顶层 `message`，因此中文产品会直接展示英文框架措辞；不同 Pydantic 版本还可能改变大小写、语序、限制描述或未知类型文本，使框架升级无意中变更外部 API。即使不包含输入值，原始 `msg` 也可能来自未来自定义 validator 的异常上下文，不应自动获得公开资格。

validation handler 以稳定错误 `type` 为输入生成中文公开消息。当前映射覆盖必填字段、文本和项目数量上下限、Literal、枚举、UUID、整数、数值、布尔、日期时间、URL、JSON 和数据结构；邮箱的通用 `value_error` 根据字段位置映射为“邮箱格式无效”。未识别类型统一返回“请求参数不合法”，不能回退到 Pydantic 原始 `msg`。响应仍保留原始稳定 `type` 与结构化 `loc`，供客户端定位字段和测试断言。

单元测试对当前 schema 实际产生的 `missing`、`string_too_long`、`too_long`、`uuid_parsing`、`enum`、`literal_error`、`int_parsing` 和数值上下界逐类断言中文结果，并向每条原始 `msg` 注入内部 Provider 与 `api_key` 文本，证明它们不会进入响应。真实重启验收重复 1100 字符密码请求，必须返回 `422/文本长度超过限制`，detail 仍只有 `type/loc/msg`，且正文不含 Pydantic 英文原文或敏感标记。

## 决策 91：个人数据 API 禁止 HTTP 缓存

Flutter 的离线能力使用安全存储中的加密缓存，并以 token SHA-256 指纹隔离账号、限制容量与有效期；但这不能控制浏览器 HTTP 缓存或中间代理。后端此前只给注册能力和邀请码管理等少数响应设置 `Cache-Control: no-store`，真实 `POST /auth/login` 的 `200` 响应同时包含 access token，却没有 Cache-Control 或 Pragma。资料原文、聊天回答、设备会话和模型 Base URL 也可能被独立缓存，绕过应用缓存的加密、清理、账号隔离和七天边界。

应用中间件因此为整个 `/api` 命名空间的所有成功与已处理错误响应覆盖 `Cache-Control: no-store` 和 `Pragma: no-cache`。策略不根据方法区分：GET、POST、PATCH、DELETE、`204`、`4xx` 与 `5xx` 都可能携带用户状态或诊断信息。ServerErrorMiddleware 外层生成的未处理 `500` 由统一 handler 显式附加相同头部，不能因异常路径绕过。OpenAPI 与其它非 API 正常页面不强制禁缓存，避免把个人数据策略扩展成无关的全站缓存政策。

回归测试分别构造 `/api` 成功 token JSON、Pydantic `422` 和未处理异常 `500`，三者都必须具备精确的 `no-store/no-cache`；非 API 成功响应不得被强制添加。真实重启验收登录本地账号，要求 token 响应和随后认证 GET 都携带两个头部，再执行 `logout-all` 并确认数据库会话为零。Flutter 仍可按既有白名单把网络响应复制到自己的加密缓存，因为 HTTP 禁缓存头只约束浏览器和代理，不改变 Dio 拦截器的显式应用存储。

## 决策 92：本地运行时设置必须串行并原子替换配置文件

运行时模型设置包含 Provider、Base URL 和 API Key。直接对 `.env` 调用 `Path.write_text` 会先截断目标再写入；进程终止、磁盘错误或文件系统异常可能留下半份配置，服务重启后全部 Provider 都可能失效。FastAPI 同步路由在线程池并发执行，两个管理员 PATCH 还可能同时读取旧文件、各自修改不同键并由后一次完整覆写丢失前一次结果；文件与进程内 `settings` 的应用顺序也可能交错。

服务使用进程内互斥锁包裹完整的校验、更新生成、文件持久化、内存应用和返回读取。文件内容写入目标同目录、唯一命名的临时文件，显式 flush 并 fsync 文件描述符，关闭后通过 `os.replace` 原子替换目标。只有替换成功才应用内存设置；任一步失败都清理临时文件并保留原 `.env` 与旧内存值。临时文件名称加入 git 忽略规则，降低进程在无法执行 finally 的极端崩溃点留下凭据后被误提交的风险。

测试在替换回调中读取目标文件，证明 `os.replace` 前旧内容从未变化；模拟替换失败后目标字节完全一致且目录无临时文件；模拟磁盘失败时内存应用函数调用次数为零；四个同步线程同时更新时活动写入者最大值严格为一。该锁只解决单进程在线设置，与决策 14 的 local/dev 范围一致。多 worker 或多实例具有独立内存，必须由部署系统统一更新环境并重启，不能把本接口当作跨实例配置分发。

## 决策 93：Embedding 配置变化必须有持久协调状态

设置 PATCH 过去先更新 `.env` 和进程内配置，再调用会自行 commit 的 `create_job()`。数据库在第二步不可用时，接口返回失败但新 Embedding 配置已经生效，数据库没有任何重建意图；服务重启只恢复已有 job，无法知道任务从未创建。检索按当前 `embedding_model` 索引身份过滤向量，模型或 Base URL 变化后可能长期召回为空；仅在异常分支尝试回滚文件也无法覆盖进程恰好终止或数据库稍后恢复。

迁移 `0021_embedding_config_state` 新增单例 `embedding_configuration_state`，保存当前已经持久协调的配置指纹，并给 jobs 增加 nullable `configuration_fingerprint` 与查询索引。指纹由稳定索引身份和 OpenAI-compatible API Key 的截断 SHA-256 摘要组成，不保存原始凭据，也不进入 `JobRead`。协调事务取得 PostgreSQL transaction-level advisory lock，比较进程当前指纹和状态；发生变化且存在可重建资料时，在同一事务添加带目标指纹的 pending 全用户任务并更新状态。相同指纹已有未结束任务时不重复创建，失败或取消后的重试携带当前指纹。

终态历史不能用于这项去重。配置从 A 切到 B 并完成 B 重建后再切回 A 时，过去成功的 A job 对应的是 B 之前的向量状态；若仅按 fingerprint 查询任意历史，会错误跳过最后一次 A 重建。复用查询因此只接受 `pending`、`running`，明确排除 `success`、`failed`、`cancelled` 和 `cancel_requested`。最后一种状态会被恢复领取直接转换为 cancelled，不会执行 worker，同样不能证明重建义务存在。旧任务仍可用于审计和手动重试，但不能证明当前数据库已满足新的配置代次。

设置 PATCH、管理员手动全局重建和全局任务重试都经过协调器。更重要的是，启动和周期恢复扫描在领取任务前执行同一协调：如果配置文件已经替换但数据库提交曾失败，状态仍是旧指纹，数据库恢复后的下一次扫描会补建并立即领取任务；任务提交成功但 HTTP 响应或内存 background dispatch 丢失时，pending job 仍由原恢复机制接管。协调 commit 会结束 advisory lock 事务，恢复器随后重新设置自己的 statement timeout 再领取任务。

首次迁移不猜测凭据历史。状态缺失时，协调器检查所有 indexed/failed 资料：无切片、切片无向量或 `embedding_model` 与当前索引身份不一致才创建一次重建；完全一致则只初始化状态，避免升级后无意义调用外部 Provider。单元测试覆盖相同状态、配置漂移、首次一致、已有同指纹活动任务和 A→B→A 回切，路由测试证明协调数据库故障返回稳定 `503` 且不派发内存 worker。真实首次重启在两份资料、两个 current `local_hash:1536` 向量下只写入一条匹配状态且任务保持零；随后把状态改成受控漂移值，恢复领取扫描补建并领取恰好一个目标指纹匹配的全局任务，验收后按新 ID 精确清理。

真实回切验收在 advisory-lock 事务内写入一个已 flush 的 `success A` 历史任务和状态 B，再以当前配置 A 执行协调。提交后数据库必须同时出现原 `success A` 与新 `pending A`，两个指纹都匹配 A 且状态回到 A，证明终态历史未抑制本轮任务；两个受控任务随后按 ID 精确清理，协调状态保持当前值。

取消中任务使用同样方法单独验收：已 flush 的 `cancel_requested A` 与状态 B 协调后，数据库同时保留原取消中任务并新增 `pending A`，不能只剩一条被错误复用；两个指纹与状态都匹配 A，受控任务随后精确清理。

## 决策 94：上传资料和索引任务必须单事务持久化

文件上传过去先调用 `create_file_document()` 提交资料和标签，再调用 `create_job()` 第二次提交。第二次数据库操作失败时，异常清理又调用需要数据库的资料删除；数据库仍不可用会留下状态 `uploaded`、文件存在但永远没有 job 的资料，任务恢复器无法发现。若第二次提交其实成功但确认响应丢失，清理物理文件还会制造已提交资料引用缺失对象。内存 BackgroundTasks 不是持久边界，HTTP 响应或进程在 commit 后退出也不能依赖它。

资料 service 拆出只 add/flush 的 `add_file_document()`，job service 复用只 add/flush 的 `add_job()`；上传路由把资料、标签关系和 `index_document` job 放进同一个 Session，只执行一次 commit。构造或 flush 失败确定没有提交时，先尽力 rollback，再删除未引用文件；rollback 本身失败只记录 traceback，不能阻止文件清理或覆盖原始异常。commit 抛错属于结果不确定状态，文件必须保留：事务若已提交，pending job 可恢复；若已回滚，文件成为可由存储审计识别的 orphan。commit 成功后的 refresh 或响应失败同样不能删除文件。

为修复旧版本遗留数据，恢复领取事务在查询 jobs 前按相同批量上限锁定 `uploaded` 非 note 资料，并用相关 `NOT EXISTS` 排除已有任意 `index_document` 历史的资料。每条缺失资料通过 `add_job()` 补入当前事务，随后同一次 claim 查询把它转换为 running 并生成 run token；资料行使用 `FOR UPDATE SKIP LOCKED`，多实例不会共同补建。已有失败或取消 job 的资料不自动重试，继续遵守显式重试产品语义。

测试覆盖成功路径只有一次 commit、job flush 失败回滚并删除文件、rollback 自身失败仍保留原异常、commit 结果不确定和 commit 后 refresh 失败均不删除文件；补偿查询断言批量上限、行锁和已有 job 条件。真实验收通过应用存储层写入受控 TXT，只提交 uploaded document，不创建 job；恢复领取补建并领取恰好一个 index_document 任务，数据库 document_id 与 run token 完全匹配，随后精确删除受控任务、资料和文件。

## 决策 95：请求集合与数据库字符串必须在存储和 SQL 前设限

Pydantic 过去只限制了资料标题，笔记和资料更新的标签列表、聊天范围，以及资料列表筛选参数仍可无限增长。上传表单还会把客户端文件名和 MIME 类型原样写入 `VARCHAR(255)` 与 `VARCHAR(128)`。超长文件名或 MIME 只有在文件已经保存、资料 flush 或 commit 时才失败，可能制造不必要的文件清理和孤立对象；超大标签或范围列表会扩大逐项标签查询、关系写入和 SQL `IN` 参数数量。

共享限制固定为每份资料最多 20 个标签、单标签 64 字符，聊天范围最多 100 个资料 ID、20 个标签和 7 种来源。资料搜索词最多 255 字符、标签筛选最多 64 字符；上传标签原始表单最多 2048 字符，文件名与 MIME 分别对齐数据库的 255 和 128 字符列。JSON schema 和 Query/Form 负责普通 API 的 `422`，上传路由在调用 storage service 前解析标签并验证文件元数据。`document_service` 在 `db.add()` 前重复验证文件字段，`tag_service` 在任何删除关系、标签查找或 flush 前重复验证数量和单项长度，内部调用不能绕过 HTTP 边界把无界输入送进数据库。

自动富化最多生成 5 个标签，但用户已提交 20 个标签时直接合并会超过统一上限。合并现在按稳定顺序优先保留已有标签，只用剩余名额加入自动标签，metadata 只记录实际应用的自动标签。旧版本可能已经持久化无数量限制的会话 scope；继续旧会话时先把资料、标签和来源收缩到新上限，标签沿用旧查询的 64 字符规范化语义，并把规范化 scope 随会话事务回写，避免升级后 500 或再次构造无界 SQL。

测试覆盖刚好位于上限的合法请求、每类集合超过一项、单标签过长和空白标签。真实路由测试证明过长筛选不会进入资料查询，文件名、MIME、标签数量或标签表单超限均不会调用存储层；service 测试证明超量标签在首条 SQL 前失败，文件字段在 `db.add()` 前失败。完整后端测试与 `compileall` 必须通过，Alembic autogenerate 不应出现迁移，因为本轮只让应用边界与既有数据库列保持一致。

## 决策 96：聊天标签和来源范围必须在检索 SQL 内求交

决策 95 限制了客户端最多提交 20 个标签，但标签数量有界不代表标签命中的资料数量有界。旧聊天路径先查询每个标签集合的全部 document ID，再查询所选来源的全部 document ID，在 Python 中与最多 100 个显式 ID 求交，最后把结果列表同时传给向量和关键词检索。一个常用标签覆盖数万份资料时，请求仍会拉取大结果集、分配大列表，并在两条后续 SQL 中构造大 `IN`；来源筛选同样会随用户资料规模增长。

检索接口现在分别接收有界的显式 `document_ids`、`tag_names` 和 `source_types`。显式 ID 继续使用最多 100 项的 `IN`；标签使用关联 `document_tags` 与 `tags` 的相关 `EXISTS`，同时限定 tag owner；来源直接使用 `documents.source_type IN (...)`。三个条件添加在向量和关键词语句的同一资料 join 上，数据库负责求交，标签组内部仍保持原有“命中任一标签”语义。`EXISTS` 不会因一份资料命中多个标签而复制切片行，检索自身的 top-k/候选 limit 继续限制返回数量。

`retrieval_service` 不能假设所有调用都来自已验证的 `ChatScope`。它在调用 embedding provider 前再次检查最多 100 个资料 ID、20 个标签和 7 种来源，并复用标签单项长度与去重校验；超限内部调用不会生成向量，也不会执行首条 SQL。测试编译向量与关键词两条 SQL，断言两者都包含标签 `EXISTS`、来源条件和唯一的显式 ID 集合；另行验证三类超限输入的 provider 与 Session 均无调用。该变化不修改表结构，不需要迁移。

## 决策 97：字段限制不能替代解析前的完整请求体字节上限

Pydantic 的 `max_length` 只在 JSON、表单或 multipart 已经被框架读取和解析后运行。攻击者仍可提交远大于任何业务字段的请求体，让进程先接收并分配内存；缺少 `Content-Length` 的 chunked 传输还会绕过只检查请求头的实现。文件上传虽然由 storage service 按文件内容流式限制为 25 MiB，但 multipart 整体还包含文件名、MIME、标签和边界，完整请求体不能简单复用文件内容上限。同步笔记创建的 `content` 此前也没有字段上限，会直接进入清洗、切片、Embedding 和富化。

应用增加纯 ASGI 请求体中间件。默认 `MAX_REQUEST_BODY_SIZE_BYTES=31457280`，先解析合法非负 `Content-Length` 并在进入内层应用前拒绝超限请求；没有可信长度时包装 `receive`，累计每个 `http.request` 消息的实际 body 字节，一旦超过同一上限即停止内层处理。稳定响应为 `413` 与“请求体超过大小限制”，显式携带 `no-store/no-cache`。中间件位于 CORS 内层和 API 禁缓存层内层，因此完整应用中的拒绝响应同时保留允许来源的 CORS 头与统一隐私头。

`MAX_REQUEST_BODY_SIZE_BYTES` 必须至少等于 `MAX_UPLOAD_SIZE_BYTES + 65536`，配置不一致时启动直接失败，避免宣称允许的文件永远无法通过 multipart 外层。笔记正文和整理结果保存统一使用 200,000 字符上限；`NoteCreate` 返回常规 `422`，`document_service` 在标题推导、文本清洗和首条数据库写入前再次检查，内部构造无法绕过。字符上限控制业务处理规模，ASGI 字节上限控制解析前内存，两者不能互相替代。

测试分别覆盖已知 Content-Length 超限、真实 chunked 迭代流累计超限、恰好位于字节上限，以及完整 `create_app()` 中 413 的 CORS 与隐私头。笔记测试覆盖恰好 200,000 字符、超出一字符的 schema 拒绝、路由不调用 service，以及绕过 Pydantic 构造时不调用清洗或 Session。完整回归和 Alembic 检查通过，本轮不修改数据库结构。

## 决策 98：同步 Provider 调用期间不能持有数据库事务或连接

认证依赖通过同一个 Session 查询登录会话和用户，因此业务 service 进入时已经有活动读事务和已 checkout 的连接。旧聊天随后读取会话与历史，在同一事务中调用查询 Embedding 和最长 90 秒的 LLM；笔记更早 flush 资料与切片，再在未提交事务中分批调用 Embedding 和摘要/标签 Provider。整理和相关资料查询也在读取 ORM 对象后直接调用外部模型。少量慢请求即可占满默认数据库池，readiness、登录和普通查询会在 Provider 仍有可用容量时先因 pool timeout 失败。简单地在 Provider 前 commit 会让半份笔记或单边用户消息提前可见，破坏原有失败原子性。

聊天拆成三个数据库阶段。第一段读取已有会话、规范化 scope 并复制最近历史，随后 rollback 释放认证与读取事务；新会话只在内存中预分配 UUID，不提前插入。第二段执行混合检索，返回完全脱离 ORM 的 `RetrievedChunk` 后再次 rollback。LLM 回答和建议问题在无数据库连接状态生成；成功后第三段对已有会话重新按 owner 查询并 `FOR UPDATE`，或插入预分配的新会话，再把 scope、用户消息和助手消息放进同一短事务提交。会话在外部调用期间被删除会稳定返回既有 404；检索、LLM 或最终 commit 失败都会 rollback，不留下新会话或半轮消息。

同步笔记采用计算后落库，而不是中途提交。资料与切片在内存预分配 UUID，纯切片函数不访问 Session；Embedding helper 生成全部向量模型，富化 helper 生成摘要和标签并只修改内存对象。所有 Provider 成功或富化按既有公开降级规则记录错误后，才在一个事务中插入 document、chunks、embeddings、标签关系并 commit。整理结果把 `ai_generated` source type 与 `source_document_ids` metadata 作为首次创建参数，消除过去 `create_note()` 已提交、provenance 第二次 commit 失败后遗留普通笔记的窗口。内部 metadata 不能覆盖规范化用户标签。

单篇整理、集合整理和相关资料查询在构造最多 24,000 字符的上下文或 2,000 字符检索查询后释放读事务，再调用 LLM/Embedding；返回的 ID 和字符串不依赖过期 ORM 属性。边界测试用可观测 Session 在每个 Provider 回调中断言连接已经释放，注入检索、LLM、Embedding 与 flush 失败并验证没有部分 add/commit。真实 PostgreSQL 验收原子创建一条笔记，得到一份 document、一个 chunk、一个对应 embedding 与标签关系；另一次真实聊天命中引用并只保存 user/assistant 两条消息。两组受控数据和临时认证会话随后按 ID 清理，全部表计数恢复。本轮不修改数据库结构。

## 决策 99：worker 的阶段 commit 后不能因 ORM 过期重新占用连接

文档 worker 已在解析、切片、Embedding 和富化之间提交状态，但 SQLAlchemy Session 默认 `expire_on_commit=True`。commit 虽然归还连接，随后 Provider 读取 `document.file_path`、`chunk.content` 或其它已加载属性时会触发隐式 refresh，重新 checkout 连接并开启读事务；代码表面上的阶段提交因此不能证明慢 OCR、语音转写、Embedding 或 LLM 期间连接已释放。任务状态函数在 commit 后执行 `refresh()`，取消检查也会开启新的读事务，进一步制造同样问题。后台 worker 数量可配置到 50，默认业务池只有 15 个连接，慢任务足以让 API 在 Provider 本身仍正常时先耗尽数据库池。

应用 `SessionLocal` 明确使用 `expire_on_commit=False`。阶段 commit 后 ORM 对象保留已经加载的快照，若业务需要并发后的新状态仍必须像现有 job 转换一样显式 `refresh()` 或重新查询，不能把隐式过期当一致性机制。文档处理在任务进度 refresh 后、Embedding 前执行统一 detach + rollback；富化前的取消检查完成后再次执行同一释放。detach 保证后续 rollback 不把 document/chunks 标记为过期，Provider 只读取内存值；Provider 返回后对象按需重新 add，数据库写入仍在明确事务中。

解析阶段在 document 状态 commit 后直接使用未过期的存储来源快照，不产生属性 lazy load。全量重建读取待处理资料后 detach + rollback，再逐份短事务查询切片；缺失切片会先创建并与最新取消检查一起 commit，然后才调用 Embedding。取消检查因此前移到昂贵 Provider 之前，任务在该点取消不会再完成一轮无用向量请求。Provider 期间独立 `JobHeartbeat` 仍使用自己的短 Session 定期续租，它不复用或长期占用 worker Session。

数据库配置测试锁定 `expire_on_commit=False`。完整 worker 事件测试模拟任务查询和 refresh 重新占用连接，并在解析、Embedding、富化三个回调中逐一断言连接已经释放；重建测试同时断言 Provider 前无连接，并修正第三个取消检查点为“不调用 Embedding”。真实运行验收上传受控 TXT，后台 job 成功生成一个 chunk 和一个对应 embedding；受控 job、document、tag、物理文件和认证会话随后按精确 ID/key 清理，全部表计数和存储 inventory 恢复。本轮不修改数据库结构。

## 决策 100：认证与任务历史维护必须离开请求路径并限批执行

签发访问 token 过去会先删除全表所有过期 `auth_sessions`，登录失败和注册额度写入也会按各自 retention 删除全表旧 `auth_login_attempts`。这些 DELETE 没有批量上限，请求延迟、锁范围和事务工作量会随历史数据增长；登录与注册 retention 不同时，使用较短 retention 的请求还可能提前删除另一策略仍有效的阻止记录。终态 `jobs` 虽不在请求路径，但只在启动时一次性删除全部过期历史，既可能让启动事务过大，也无法在长期不重启的实例中持续收敛。

应用使用统一 maintenance service 清理过期会话、旧限流记录和终态任务。每张表先按到期时间或更新时间及主键稳定排序，在候选 CTE 中使用 `LIMIT MAINTENANCE_CLEANUP_BATCH_SIZE` 与 `FOR UPDATE SKIP LOCKED`，再只删除该批候选；默认每表每轮 1000 行、配置范围 1–10000。三张表共用数据库 `now()` 和一个短事务，限流 cutoff 取登录与注册 retention 的较大值，终态任务继续遵守 `JOB_RETENTION_DAYS`。

维护在应用启动和每次任务恢复周期中通过 `asyncio.to_thread` 执行，并复用 `JOB_RECOVERY_STATEMENT_TIMEOUT_SECONDS`。超过一批的积压由后续周期逐步清理，多实例可以跳过彼此已锁定的候选；维护失败与恢复扫描一起记录并在下一轮重试。token 签发只淘汰当前用户超过活跃会话上限的旧会话，限流请求只查询或 upsert 自己的 HMAC 作用域，不再承担全局维护。测试编译 PostgreSQL DELETE，锁定 CTE、稳定排序、批量上限、跳锁、共享 cutoff 与单事务行为，并验证请求路径不含清理 DELETE。

## 决策 101：限批删除还必须有与候选排序匹配的数据库索引

`LIMIT` 只能限制最终锁定和删除的行数，不能自动限制数据库寻找候选的工作量。`auth_sessions.expires_at` 与 `auth_login_attempts.updated_at` 已有时间索引，但 `jobs` 只有用户、状态和外键索引；周期维护按 `updated_at, id` 查找最旧终态任务时，历史增长后仍可能每轮全表扫描并排序，最终触发恢复 statement timeout，使维护与任务认领一起失败。

任务表增加普通 B-tree 索引 `ix_jobs_updated_at_id(updated_at, id)`。普通复合索引与参数化 cutoff 和排序稳定匹配，避免部分索引在 `status IN` 使用绑定参数或服务器通用计划时无法被证明适用；扫描先按时间范围和顺序取候选，再过滤三个终态。该索引也保留主键作为稳定同时间排序，不改变清理语义。

迁移 `0022_jobs_updated_at_index` 在 Alembic `autocommit_block` 中使用 `CREATE INDEX CONCURRENTLY`，避免已有大任务表升级时由普通建索引长时间阻塞插入、心跳和状态转换；降级同样并发删除索引。模型测试锁定索引列顺序，真实 PostgreSQL 系统目录验证定义，并在禁用顺序扫描后用 `EXPLAIN` 确认维护候选查询执行 `Index Scan using ix_jobs_updated_at_id`，时间 cutoff 进入 `Index Cond`。

## 决策 102：恢复候选和任务历史分页需要各自匹配的稳定排序索引

任务历史维护索引只解决终态数据清理。周期恢复查询跨用户筛选 `pending`、`cancel_requested` 和 stale `running`，再按 `created_at` 领取最早任务；已有 `(user_id, status)` 索引以用户为首列，不能自然提供全局创建顺序，执行计划仍需要收集活跃状态并排序。用户任务历史则按 `updated_at DESC, created_at DESC` 做 offset 分页，既没有匹配的用户内排序索引，也没有唯一终极排序键；多个任务时间戳相同时，数据库可以用不同顺序返回，造成静态数据跨页重复或遗漏。

恢复查询增加固定的活跃状态前置谓词，并创建部分 B-tree 索引 `ix_jobs_recoverable_created_at_id(created_at, id) WHERE status IN ('pending', 'cancel_requested', 'running')`。谓词是应用枚举常量，不含用户输入，并以 SQL 字面量进入语句，使 PostgreSQL 在参数化 stale cutoff 和状态分支之外仍能证明部分索引适用。索引只保存活跃任务，按全局创建时间直接扫描到批量上限，不读取终态历史，也不再执行 Sort；任务进入终态后自动移出索引。

历史列表排序补为 `updated_at DESC, created_at DESC, id DESC`，并创建 `ix_jobs_user_updated_created_id(user_id, updated_at, created_at, id)`。固定用户条件下 PostgreSQL 可反向扫描普通升序索引，`id` 为相同时间戳提供唯一稳定顺序；status 和 job type 筛选继续由现有索引与 planner 选择处理。该调整保持既有页码、总数和响应格式，不把 API 扩张为新的游标分页协议。

迁移 `0023_job_query_indexes` 在 Alembic autocommit block 中并发创建和删除两个索引，并使用 `IF NOT EXISTS/IF EXISTS` 让并发建索引完成后、版本号写入前进程中断的重试可以收敛。真实 PostgreSQL 往返执行 `0023 -> 0022 -> 0023`；系统目录确认索引均 ready/valid，`EXPLAIN` 确认恢复查询使用部分索引且无 Sort，默认历史查询使用用户复合索引的 Index Only Scan Backward 且无 Sort。

## 决策 103：所有 offset 分页必须有唯一排序后缀和匹配的作用域索引

任务历史之外还有资料、会话、消息、标签和注册邀请码使用页码分页。标签按用户内唯一的名称排序，邀请码已经按 `created_at, id` 排序，二者顺序稳定；资料只按 `created_at`、会话只按 `updated_at`、消息只按 `created_at`，同一事务批量插入或数据库时间戳相同时没有唯一顺序。即使数据在翻页期间不变化，PostgreSQL 也可以在相同排序键内部使用不同物理顺序，造成相邻 offset 页重复或遗漏。资料、会话和消息原有索引还只能过滤作用域，不能同时提供分页顺序。

资料列表改为 `created_at DESC, id DESC` 并使用 `ix_documents_user_created_id(user_id, created_at, id)`；会话列表改为 `updated_at DESC, id DESC` 并使用 `ix_conversations_user_updated_id(user_id, updated_at, id)`；消息列表和最近聊天上下文分别按 `created_at, id` 正序与倒序，并共用 `ix_messages_conversation_created_id(conversation_id, user_id, created_at, id)`。消息索引同时包含所有权条件，避免查询为额外的 `user_id` 过滤放弃顺序扫描。内部选择最近资料的整理查询也补 `id` 后缀，复用资料索引。管理员邀请码保留既有稳定顺序，并增加 `ix_auth_registration_invites_created_id(created_at, id)`。

迁移 `0024_stable_pagination` 先并发创建四个新索引，确认 ready 后再并发删除被新索引前缀完全覆盖的 `ix_documents_user_id`、`ix_conversations_user_id`、`ix_conversations_user_updated` 和 `ix_messages_conversation_id`，索引总量不会因修复持续膨胀；downgrade 先恢复旧索引再移除新索引。所有操作使用 `IF NOT EXISTS/IF EXISTS`，真实 PostgreSQL 已完成 `0024 -> 0023 -> 0024` 往返迁移。默认计划中资料、会话和邀请码直接使用目标索引且无 Sort；当前每会话消息极少时 planner 可以选择成本更低的 Bitmap Scan 加小型 Sort，关闭 bitmap scan 后验证同一 SQL 可使用消息复合索引无 Sort 顺序扫描，数据增长时无需更改查询。

## 决策 104：子串搜索需要 trigram 候选索引并保留字段级语义复核

资料列表对标题、原文、清洗正文和摘要执行四路 `%keyword%`，会话历史对标题执行同类搜索。B-tree 作用域索引只能先缩小到某个用户，随后仍需逐行读取和扫描大文本；计数与当前页查询各执行一次，正文规模增长后成本会同时放大。旧实现还直接把用户输入包在 `%` 中，输入 `%` 或 `_` 会被 PostgreSQL 当作通配符而不是字面字符，导致搜索结果远超用户表达的关键字。

应用统一使用 `escape_like_pattern()` 按顺序转义反斜杠、`%` 和 `_`，所有 `ILIKE` 显式声明反斜杠 escape。资料搜索构造标题、原文、清洗正文和摘要的合并文本，并先对该表达式执行同一字面子串条件；任何单字段命中都必然命中合并表达式，因此它是原四路 OR 的必要条件。查询随后仍执行原四字段 OR 复核，排除关键字跨字段边界形成的假命中，搜索语义不放宽也不缩窄。混合检索的关键词 LIKE 同样复用统一转义函数，避免两条搜索路径逐渐产生不同规则。

迁移 `0025_trigram_search` 安装 PostgreSQL `pg_trgm`，为合并资料文本创建 `ix_documents_search_trgm` GIN 表达式索引，并为会话标题创建 `ix_conversations_title_trgm`。2 万行探针中，合并表达式索引约 8.4 MiB，四列分别维护 postings 的多列 GIN 约 13.3 MiB；前者减少约 36% 且只需一次 Bitmap Index Scan。两个索引使用并发创建和幂等名称，downgrade 只并发删除项目索引，不删除可能被其它对象使用的扩展。

资料标签筛选同时补上 `Tag.user_id == user_id`。这不仅把所有权约束显式下推到关联 SQL，也使现有 `uq_tags_user_name(user_id, name)` 可以直接定位 tag，再由 `ix_document_tags_tag_id` 找到资料关系；过去只按 name 会跳过唯一索引首列并扫描所有用户的同名标签。真实 PostgreSQL 验收确认扩展版本、索引 ready/valid、字面 `%/_` 行为、GIN Bitmap Index Scan、标签唯一索引和 tag-id 关联索引；`0025 -> 0024 -> 0025` 往返迁移与 Alembic autogenerate 均通过。

## 决策 105：关键词候选必须先全局评分再限批，不能依赖表物理顺序

混合检索过去先对 `Document.title`、`DocumentChunk.content` 和 `section_title` 的 OR 命中执行 `LIMIT max(6 × top_k, 24)`，SQL 没有 `ORDER BY`；应用拿到数据库任意返回的一小批 chunk 后才计算词频和标题加权分数。候选上限虽然限制了 Python 内存，却把最终相关性绑定到 heap 或索引物理顺序：更晚插入但重复命中更多关键词的 chunk 可能永远不进入 rerank。跨 document 与 chunk 两张表的直接 OR 也阻止各自 trigram 索引生效；2 万行探针的执行计划对两表都使用顺序扫描。

关键词查询拆成两个可索引候选分支。chunk 分支对 `coalesce(content, '') || ' ' || coalesce(section_title, '')` 执行 trigram 条件，资料分支对已索引的 `Document.title` 执行同类条件并通过 document ID 找到 chunk；两支都显式限制 chunk owner，使用 SQL `UNION` 对同时命中标题和正文的 chunk ID 去重。最终查询重新关联 chunk 与资料、应用资料 ID/标签/来源/exclude 等原作用域条件，并保留原三字段 OR 做语义复核。

数据库排序表达式与 `_keyword_score` 保持同一公式：把标题、章节和正文小写合并，对最多 10 个规范关键词计算非重叠出现次数，命中数最多计 6 次、标题命中最多计 3 次，分别按 0.05 和 0.06 加到 0.55 基础分；相同分数按 chunk UUID 稳定排序。只有完成全局排序后才应用候选上限，Python 继续计算公开分数并执行既有混合 rerank，不改变响应结构或最终 top-k 契约。

迁移 `0026_chunk_search` 并发创建 `ix_document_chunks_search_trgm` GIN 表达式索引，并与 PostgreSQL 反射后的规范表达式对齐，Alembic 不会误判删建。2 万行计划确认 chunk 和 document 两支分别执行目标 Bitmap Index Scan；受控真实验收插入 30 个匹配 chunk，把 6 次命中的最高分项放在最后，`top_k=1` 仍选中旧无序 `LIMIT 24` 会漏掉的第 30 项，随后按资料 ID 级联清理并恢复表计数。`0026 -> 0025 -> 0026` 往返迁移、全量测试与 autogenerate 均通过。

## 决策 106：带作用域过滤的 HNSW 必须启用有界 iterative scan

pgvector 的 HNSW 默认先按向量近邻扫描 `ef_search` 个候选，再应用 `user_id`、embedding model/dimensions、资料、标签、来源和 exclude 等普通 SQL 条件。过滤选择性较高时，即使数据库中存在足够多的合格向量，过滤后的结果也可能少于 `top_k`；扩大应用层 `LIMIT` 不能解决，因为近似索引在该层之前已经停止。当前环境 pgvector 0.8.2 的默认值为 `hnsw.iterative_scan=off`、`hnsw.ef_search=40`。

每次 `vector_search()` 在 Provider 生成查询向量后、执行 HNSW SQL 前，通过统一 helper 在当前事务调用三项 `set_config(..., true)`：`hnsw.iterative_scan=strict_order` 保持距离顺序并在过滤不足时继续扫描，`HNSW_EF_SEARCH` 控制初始候选广度，`HNSW_MAX_SCAN_TUPLES` 为继续扫描提供硬预算。默认分别为 100 和 20000，配置范围限制为 1–1000 与 1–1000000；事务提交、回滚或连接归还后设置自动恢复，不能污染其它请求。iterative scan 改善过滤后的候选完整性，但仍受最大扫描预算约束，不承诺在极端选择性下进行无界精确全表检索。

readiness 的 vector 检查不再只判断扩展存在，而是在 SQL 中要求 pgvector 主/次版本至少 0.8；旧版本不支持 iterative scan 时实例保持 not ready。readiness 和 capabilities 同时暴露 `strict_order`、ef search 与最大扫描量，部署者可以在召回完整性、延迟和 CPU/内存之间调整，而无需修改代码。版本检查与 HNSW index 检查仍在健康查询 statement timeout 内完成。

真实 PostgreSQL 受控验收构造 120 个更近但 embedding model 不匹配的向量和 12 个较远且匹配的向量，`ef_search=10` 且 iterative scan 关闭时过滤结果为 `0/8`，启用 `strict_order` 后为 `8/8`。生产 `vector_search()` 使用默认有界配置再次返回 8 个高于公开相关度阈值的目标结果；受控资料、132 个 chunk 和 embedding 随后按资料 ID 级联清理，三表计数恢复。配置、事务 GUC、版本 readiness 和 SQL 调用顺序均有单元测试覆盖。

## 决策 107：HNSW readiness 必须验证索引结构，名称存在不代表可用

旧 readiness 只在 `pg_indexes` 中检查 `ix_chunk_embeddings_embedding_hnsw` 这个名称是否存在。同名普通 B-tree、错误列或 opclass 的索引也会被报告 ready；`CREATE INDEX CONCURRENTLY` 失败可能留下 `indisvalid=false` 的索引壳，名称仍存在但 planner 永远不会使用。数据库向量列或索引距离策略被人工修改后，同样可能在健康检查全绿时让检索退化为顺序扫描或使用错误距离语义。

索引检查改为关联 `pg_class`、`pg_namespace`、`pg_index`、`pg_am`、`pg_attribute` 和 `pg_opclass`。兼容索引必须位于当前 schema，属于 `chunk_embeddings`，relation kind 为 index，access method 为 `hnsw`，同时 `indisready/indisvalid/indislive`；它必须是单个非唯一普通键，没有表达式和部分谓词，列名为 `embedding`，数据库类型精确为 `vector(1536)`，operator class 精确为 `vector_l2_ops`。任一条件不满足时，readiness 与 capabilities 都把索引视为 missing，不暴露内部 catalog 诊断。

真实 PostgreSQL 在一个未提交 DDL 事务中先把正确 HNSW 改名，再创建同名 `user_id` B-tree；新检查返回 false，证明名称不能绕过结构契约。事务回滚后从新连接检查真实 HNSW 返回 true，未修改持久 schema，也未让运行中的其它连接看到伪索引。单元测试锁定所有关键 catalog 条件，完整回归和 Alembic autogenerate 通过。

## 决策 108：HNSW 参数必须显式化，线上重建必须先建后切并可恢复

最初的 `0009_vector_index` 使用普通 `CREATE INDEX IF NOT EXISTS`，未声明 HNSW build options。已有大量 embedding 的数据库升级到该迁移时会在建索引期间阻塞相关写入；扩展默认的 `m` 与 `ef_construction` 也没有进入模型或 readiness 契约，pgvector 默认值变化、人工重建参数不同或同名索引漂移都无法被 Alembic 和健康检查发现。当前索引 `reloptions` 为空，虽然实际等价于 pgvector 0.8.2 的默认 `m=16 / ef_construction=64`，但该等价关系只存在于扩展实现中。

模型索引显式声明 `m=16` 与 `ef_construction=64`。`m` 控制每个节点的最大连接数和索引内存，`ef_construction` 控制构建期候选广度与召回质量；本轮固定当前经过运行验证的默认平衡，不把 schema 级参数伪装成可热更新运行配置。readiness 在既有结构条件之外要求 `reloptions` 精确包含这两项且没有额外项，参数漂移会立即使实例 not ready。

迁移 `0027_online_hnsw_options` 使用临时 replacement 索引执行 `CREATE INDEX CONCURRENTLY`，旧 HNSW 在完整构建期间继续服务查询；replacement ready/valid/live 且参数匹配后，才并发删除旧索引并用元数据 rename 切换标准名称。迁移每次运行先检查目标是否已满足契约：名称切换后但 Alembic 版本未写入时直接幂等成功；replacement 已建成时直接复用；无效或参数错误的 replacement 先并发删除再重建；旧索引已删除时仍可把已完成 replacement 切换回来。downgrade 同样先并发建立默认参数 replacement，再删除显式参数索引，不制造阻塞式回退。

真实 PostgreSQL 已完成 `0027 -> 0026` downgrade 和 resumed upgrade。验收还模拟迁移在 replacement 并发建成后中断：数据库同时保留旧默认索引和有效的显式参数 replacement，恢复 upgrade 复用后者并收敛为唯一标准名称，最终 `reloptions=['m=16','ef_construction=64']`、ready/valid、readiness compatible；强制索引计划继续执行 `Index Scan using ix_chunk_embeddings_embedding_hnsw`。临时索引名称无残留，完整测试和 Alembic autogenerate 通过。

## 决策 109：页码 OFFSET 必须有工作量边界，完整遍历使用 keyset cursor

所有列表路由过去只校验 `page >= 1`，service 直接计算 `(page - 1) * page_size`。Python 接受任意精度整数，但 PostgreSQL/psycopg 的 OFFSET 参数有有限整数范围；真实 API 传入超大页码会落入数据库驱动并返回稳定边界之外的 `500`。即使整数没有溢出，任意深 OFFSET 仍要求数据库跳过此前全部结果，调用成本可以由一个很小的认证请求放大。单独给 page 设置较小固定上限又会破坏标签、会话消息和资料选择器“逐页加载全部”的既有语义。

普通页码 API 因此保留响应格式、总数和筛选参数，但统一限制最多跳过 100,000 行。路由先限制 page 的绝对数值，所有六个 service 再按实际 page size 计算并校验 offset；超界在 count/list SQL 前抛出命名分页异常，由全局 handler 映射为稳定 `422`。这既阻止任意精度整数进入驱动，也防止绕过 HTTP 直接调用 service 形成深扫描。页面 UI、会话历史、任务历史和邀请码管理继续使用页码，超过边界时明确失败而不是静默返回空页。

Flutter 中确实需要完整集合的三个流程改用独立 scan API：标签按用户内唯一 `name` 升序，资料按 `(created_at, id)` 降序，消息按 `(created_at, id)` 升序执行 keyset 条件。每次 SQL 读取 `page_size + 1` 行，以额外一行精确判断是否生成 `next_cursor`，响应不执行 count，也不靠满页猜测后续数据。游标是 URL-safe Base64 编码的版本化 JSON，包含端点 kind 和排序键；客户端只原样回传，服务端拒绝格式错误、超过 512 字符、类型不匹配或跨端点游标。它不是授权凭据，所有查询仍独立执行用户和会话所有权过滤；资料游标请求必须保持原筛选条件。

现有 `(user_id, created_at, id)`、`(conversation_id, user_id, created_at, id)` 和 `(user_id, name)` 索引直接覆盖三条 keyset 路径，不需要新迁移。Flutter 离线缓存白名单同步包含 scan 路径，响应体中的 next cursor 与 items 原子缓存。回归测试覆盖六个 service 在任何数据库调用前拒绝超界 offset、游标往返/损坏/跨端点、三类 SQL 无 OFFSET 且使用一行 lookahead、Flutter 两批完整遍历和缓存重验证；真实 API 复现由原 `500` 收敛为 `422`，并以 `page_size=1` 验证三个 scan 接口可连续取下一批且不重复。

## 决策 110：标签合并和删除必须使用集合化 SQL 与数据库级联

标签重命名为已有名称时，旧实现先把源标签的全部 document ID 读成 list，再把目标标签的全部 document ID 读成 set，在 Python 中逐项求差并创建 ORM 关系；随后 `db.delete(source_tag)` 因 `cascade="all, delete-orphan"` 又加载源标签的完整关系集合并逐项删除。单次认证 `PATCH /tags/{id}` 的内存、SQL 参数和 ORM identity map 因此随标签覆盖资料数无界增长。普通 `DELETE /tags/{id}` 使用相同 ORM 删除路径，也会在删除一个常用标签时物化全部关系。两份资料、三条关系的真实事务探针已经发出 9 条 SQL，其中包含两次关系 ID 全量读取、关系集合加载、插入和逐关系删除；规模增大后不是固定成本。

更新路径先规范化名称，再用一个 owner 约束查询同时匹配源 ID 和目标名称。`(user_id, name)` 唯一约束与主键保证结果最多两行；查询按 UUID 升序并执行 `FOR UPDATE`，两个相反方向的并发合并也按相同顺序取得标签锁。外键插入对源标签取得的 key-share 锁会等待这次行锁，源被删除后不能在迁移 SQL 与删除之间静默新增一条随后被级联丢弃的关系。

关系迁移改为单条 PostgreSQL `INSERT INTO document_tags (document_id, tag_id) SELECT document_id, :target_id FROM document_tags WHERE tag_id=:source_id ON CONFLICT (document_id, tag_id) DO NOTHING`。源独有关系获得新的目标关系，源与目标重叠的资料保留既有目标关系；复合主键负责去重。随后执行带 source ID 和 owner 的直接标签 DELETE，`document_tags.tag_id ON DELETE CASCADE` 在数据库内移除全部源关系。普通删除也直接执行 `DELETE FROM tags WHERE id=:id AND user_id=:user_id`，用 rowcount 区分 204 与 404；模型关系设置 `passive_deletes=True`，防止未来 ORM 删除重新加载未访问的关系。

集合化实现对同一两资料探针固定为 4 条 SQL：最多两行的加锁查询、insert-select、标签 delete 和返回对象 refresh；验证源标签为 0、目标关系为 2、不同资料数为 2，外层事务随后回滚。单元测试锁定 `FOR UPDATE` 稳定顺序、insert-select、复合冲突处理、owner delete、零 rowcount 不提交和 passive delete；真实 API 再次完成合并 200 与删除 204，受控关系最终为 0。完整后端 437 项、compileall 与 Alembic check 通过；本轮只复用既有主键、唯一约束、外键级联和索引，不需要迁移。

## 决策 111：文件向量化必须限制常驻内存且保持整份索引原子替换

文件上传允许最多 25 MiB，默认切片约 600–900 个字符并带 overlap，一份接近上限的纯文本可能产生数万条 chunk。旧 `embed_document_chunks()` 虽然每 64 条调用一次 Provider，却把每批返回的 1536 维 Python float list 转成 ORM 对象后持续追加到同一个 `embeddings` 列表，直到全部外部调用成功才统一 `add_all + flush`。单个 float 在 Python 中远大于数据库中的 float32，向量和 ORM identity map 可把一份合法文件放大到 GiB 级常驻内存；多个普通上传或恢复 worker 并行时会先耗尽进程内存。批量 Provider 请求限制了单次网络正文，但没有限制整份结果累计。

不能简单在每个 Provider 批次后提交：重建期间会暴露部分新索引，后续 Provider 失败还会永久丢失旧向量。也不能用一个未提交事务跨越全部 Provider 调用，因为连接必须留在该事务上，会撤销决策 98 的连接池边界。文件向量化因此分为两个阶段。第一阶段只调用 Provider，把每批结果校验数量和维度后转换为紧凑 float32，顺序写入 `SpooledTemporaryFile`；前 8 MiB 保留在内存，超过阈值自动滚动到匿名临时文件，句柄关闭或进程结束时由操作系统清理，不生成应用可引用的持久路径。此阶段没有 delete、insert 或 flush SQL，Provider 任一批失败时旧索引完全不变。

全部 Provider 批次成功后才进入数据库阶段。服务在调用方现有事务中删除当前资料旧向量，按相同 batch size 从 spool 读取 float32、还原当前批次的 ORM 向量、`add_all + flush`，随后逐个 `expunge` 已 flush 对象；常驻 Python 向量和 ORM 集合因此最多是一个 Provider/数据库批次，加上最多 8 MiB 紧凑内存 spool。服务只返回持久化数量，不再返回整份 ORM 列表，也不自行 commit。所有批次完成后 worker 统一提交；任一数据库批次失败仍由既有异常路径 rollback，旧 delete 和此前新 insert 一起回滚。同步笔记继续受 200,000 字符正文上限约束，文件和重建路径使用本决策的 spool。

测试覆盖 `2/2/1` 三批 Provider 全部先于首条数据库 SQL、每批 flush 后 detach、Provider 第二批失败时数据库零调用、向量数量/维度错误、数据库第二批失败时不擅自 rollback、按需加载 chunk 后在 Provider 前释放读事务、1 字节阈值强制滚动匿名临时文件，以及非法 batch size。真实 PostgreSQL 先提交 5 条旧向量：受控 Provider 第二批失败后旧模型仍为 5 条；成功路径按 `2/2/1` 替换后新模型恰好 5 条、旧模型为 0、不同 chunk 为 5，随后按资料 ID 级联清理。完整后端 447 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 112：索引重建必须按轻量稳定键扫描，不能物化全部资料

决策 111 限制了单份资料的向量常驻内存，但重建任务仍先执行 `documents = list(select(Document)...)`。`Document` 包含原文、清洗正文、摘要、metadata 和错误文本；全用户任务会在首个 Provider 调用前把所有用户符合状态的完整资料同时装入 Session 和 Python list，内存随资料总量与正文规模无界增长。逐份失败时又把每个标题和错误追加到 `failed` list，尽管最终响应只使用前三条，最坏情况下仍保留全库失败文本。全局 advisory lock 只防止两个全用户重建并行，不能限制这两个集合。

重建开始时记录 UTC 时间上界，只统计并扫描 `created_at <= scan_started_at` 且状态为 `indexed/failed` 的资料；用户任务额外限定 owner。键扫描按 `(user_id, created_at, id)` 升序，每批只选择这三个轻量列并限制 100 行，后续批次使用 tuple `>` keyset。三列顺序唯一且创建时间、owner 在正常生命周期不随重建状态更新变化，现有 `ix_documents_user_created_id(user_id, created_at, id)` 同时覆盖全用户和固定用户顺序，不需要 OFFSET、Sort 或新索引。扫描开始后新建的资料明确留给下一轮，不让长任务追逐持续写入。

每个键在处理前重新按 ID、状态、owner 和时间上界读取一份完整资料。等待期间已删除、转为处理中状态或不再属于范围的行直接跳过；成功读取后先 expunge 该资料并 rollback，再 yield 给进度更新、chunk 读取和 Provider 阶段。键批次查询同样在返回批次前 rollback，因此不使用会跨越外部调用的服务器端 cursor，也不让 keyset generator 隐式持有连接。每份成功、无正文失败或异常处理结束后再次统一释放 Session，identity map 不跨资料增长。初始 count 只用于进度分母，进度上限固定为 94，以容忍极少数扫描开始前插入但稍后提交的可见性变化。

失败聚合改为独立 `failed_count` 和最多三项 `failed_samples`；任务消息仍报告完整失败数量，公开错误摘要保持原有前三项加“另有 N 份失败”语义。测试覆盖首批与后续 tuple cursor、100 行 limit、count 与扫描条件一致、完整资料二次校验、非法 batch size 在 SQL 前失败、10 份失败只保留三份样本。真实 PostgreSQL 以 `batch_size=1` 扫描两份资料，每次 yield 都验证无活动事务、identity map 为 0、连接池 checked-out 为 0；禁用顺序扫描后计划直接使用 `Index Scan using ix_documents_user_created_id`，时间上界进入 Index Cond 且没有 Sort。完整后端 454 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 113：账号删除必须集合化锁定并批量写入存储删除 outbox

账号删除过去会把用户的全部 job ID 和完整 `Document` ORM 对象物化到 Python，再构造全部存储位置集合并逐文件插入 outbox。`Document` 包含原文、清洗正文、摘要和 metadata；单次认证请求的内存、identity map 与 SQL 数量因此会随资料规模无界增长。逐条 enqueue 还会让重复存储位置在应用层占用集合内存，数据库已经存在的位置则继续产生逐条冲突检查。

用户行仍先使用 `FOR UPDATE` 锁定，阻止新的外键所有权行进入删除范围。现有 job 和 document 分别通过只选择 `id`、按 `id` 排序并 `FOR UPDATE` 的 CTE 锁定，外层 `count(*)` 完整消费 CTE 但只向 Python 返回一个标量；既保留稳定锁顺序与事务 fencing，也不加载正文或 ID 列表。锁定后用数据库 `EXISTS` 检查任一非空文件路径是否缺少 backend/scope，校验失败时不写 outbox、不删除业务数据且不提交。

文件删除意图改为一条 PostgreSQL `INSERT ... SELECT DISTINCT`：内层按 `(storage_backend, storage_scope, file_path)` 去重，外层为每个位置生成 UUID 和初始 attempts，再用既有 `uq_storage_deletions_location_key` 执行 `ON CONFLICT DO NOTHING`。outbox 插入、业务表删除和用户删除仍在同一事务中提交，不改变 worker 唤醒与失败回滚语义。测试断言账号删除链路不再调用 `scalars()`、锁定 SQL 只选择主键、provenance 使用 `EXISTS` 且 outbox 使用集合化 SQL。真实 PostgreSQL 在外层回滚事务中删除含三份资料和一个任务的临时账号，其中两份资料共享同一存储位置；用户、资料和任务归零且 outbox 恰好一条，回滚后四张表恢复基线、连接池 checked-out 为 0。完整后端 454 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 114：普通任务与恢复任务必须共享真实 worker 并发上限

上传、重试和手工重建过去通过 FastAPI `BackgroundTasks` 进入 AnyIO 线程池，恢复 worker 则通过 `asyncio.to_thread` 进入事件循环的默认执行器。`JOB_RECOVERY_MAX_ACTIVE_WORKERS` 只统计恢复 task，普通 worker 可以在另一容量域同时运行；两个线程池叠加后，进程内 Provider 调用、向量 spool 和短数据库阶段的真实并发没有统一上限。仅在两个入口各放一个同值 semaphore 仍会允许上限相加，也无法阻止恢复器先把大量任务 claim 为 `running` 再排队。

所有资料处理和索引重建入口现在共享一个进程级 `JobWorkerLimiter`，实际 permit 总数使用既有 `JOB_RECOVERY_MAX_ACTIVE_WORKERS`。普通 `BackgroundTasks` 注册异步包装：等待 permit 时留在事件循环，不占用 AnyIO 的同步路由线程；取得 permit 后把同步 pipeline 提交到 asyncio 默认执行器。恢复扫描先按恢复状态预留本轮容量，再从共享 limiter 非阻塞预留剩余 permit，只按实际取得的数量执行数据库 claim；没有容量时直接跳过 claim，因此不会制造持有 run token 但尚未开始执行的长队列。任务的 `pending/running` claim、run token、心跳和晚到 worker 防护保持不变。

permit 由底层同步线程的 `finally` 释放，而不是由 asyncio 包装 task 的生命周期释放。关闭超时或请求取消若只取消包装 task，真实线程仍占用槽位；线程退出前新的普通或恢复 worker 都不能突破上限。线程安全等待队列在槽位释放时把 permit 直接移交给下一项异步等待，不让等待者占用执行器线程。readiness 新增统一 occupied、waiting 和 max 三项指标，同时保留只反映恢复 supervisor 的原 active worker 指标。测试覆盖 6 个任务在上限 2 时并发峰值严格为 2、普通 worker 占满容量时恢复扫描不调用 claim、包装取消后线程退出前无法再次预留槽位，以及所有普通路由均注册异步限流包装。完整后端 457 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 115：认证会话上限必须由集合化裁剪和显式查询上限共同保证

访问 token 签发过去虽然把正常账号限制为最多 10 个活动会话，但实现先用 OFFSET 查询该账号所有待淘汰 session ID，调用 `.all()` 物化完整列表，再构造 `DELETE ... WHERE id IN (...)`。正常生命周期只有极少结果不能证明请求工作量有界；旧版本、人工导入、并发异常或约束外数据一旦积累大量会话，一次登录就会分配大列表并生成大量绑定参数。设备会话列表同样没有 SQL `LIMIT`，只依赖每次签发都成功维护上限这一间接不变量。

签发继续先对用户行执行 `FOR UPDATE`，同一账号的注册、登录和改密换发因此保持串行。旧会话裁剪改为 `stale_auth_sessions` CTE：按 `created_at DESC, id DESC` 稳定排序，跳过固定的 `AUTH_MAX_ACTIVE_SESSIONS_PER_USER - 1` 行，再由同一条 `DELETE` 在数据库内删除其余行；应用不读取任何旧 ID，SQL 参数数量固定。新会话仍在裁剪后加入同一事务，最终保留最新 N-1 个既有会话和当前会话。显式注销、全部注销、改密撤销以及 token 声明不变。

`GET /auth/sessions` 现在同时按 owner、未过期和稳定倒序过滤，并在 SQL 中应用 `AUTH_MAX_ACTIVE_SESSIONS_PER_USER` 限制；即使历史数据违反正常上限，请求返回和 ORM identity map 仍有硬边界。测试 fake 刻意不向签发路径提供 `scalars()`，并断言裁剪 SQL 只有 owner 与 OFFSET 标量参数、没有 ID 集合。真实 PostgreSQL 外层回滚事务插入 250 个旧会话，签发后准确保留最新 9 个旧会话与 1 个当前会话，列表返回 10 项且只标记一个当前项；回滚后用户与会话计数恢复，连接池 checked-out 为 0。完整后端 457 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 116：大文件切片必须从生成到向量持久化全程限批

决策 111 限制了高维向量结果的常驻内存，但文件 worker 仍先让 chunker 构造完整 `list[ChunkData]`，再构造整份 `list[DocumentChunk]` 并一次 `add_all`；Embedding 第一阶段随后加载同一资料的全部 chunk ORM，富化虽然只读取前 8 项，却继续持有完整列表到任务结束。25 MiB 文件可能产生数万切片，正文字符串、两层切片对象、Session identity map 和 Provider 输入快照会在同一 worker 中叠加；决策 114 的并发上限只能限制放大倍数，不能让单个合法文件的内存随批次有界。

chunker 增加惰性 `iter_text_chunks()`，段落扫描和超长段落拆分都使用生成器，不再先调用 `text.split()` 或构造完整 piece 列表；原 `split_text_into_chunks()` 保留为同步笔记等有硬正文上限调用方的兼容列表包装。文件和缺失切片重建使用默认 256 条的持久化批次：每批创建 ORM、`add_all + flush` 后逐条 expunge，再继续消费生成器。旧切片删除与所有新批次仍处于调用方同一事务，任何生成或 flush 失败不自行 commit/rollback，由 worker 的既有异常路径整体回滚。

文件与重建 Embedding 不再接收完整 chunk list。第一阶段使用现有唯一约束索引按 `document_id` 和递增 `chunk_index` keyset 扫描，每批只选择 `id/chunk_index/content`；每次查询结果复制成轻量输入后立即 rollback，再调用 Provider。spool 记录从纯向量扩展为 16 字节 chunk UUID 加定长 float32 向量，仍只在前 8 MiB 使用内存；全部 Provider 批次成功后才删除旧向量，并直接从 spool 按批构造、flush、detach 新 ORM。Provider 失败仍是零向量写入，数据库阶段失败仍由同一事务恢复旧 delete。富化查询显式 `LIMIT 8`，其 Provider 上下文继续限制为 6,000 字符；同步笔记的 200,000 字符上限和原子创建语义不变。

测试覆盖长段落惰性生成、切片按 `2/2/1` 时边生成边 flush、flush 失败不擅自 rollback、存储 chunk 按 `2/2/1` keyset 查询且每批 Provider 前释放读事务、UUID+向量 spool 按批落库、Provider 与数据库失败原子性、富化固定 `LIMIT 8`，以及 worker 恢复和取消契约。真实 PostgreSQL 用 5,000 字符长段落生成 8 个 chunk，`batch_size=2` 持久化后 identity map 中 chunk 为 0；Provider 第二批失败后旧 8 条向量完整保留，成功路径按 `2/2/2/2` 替换为 8 条新向量，每次 Provider 回调均无活动 Session 事务且连接池 checked-out 为 0。禁用顺序扫描后的计划使用 `Index Scan using uq_document_chunks_document_index` 且没有 Sort；受控数据清理后四表计数恢复。完整后端 465 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 117：解析阶段必须避免正文与媒体请求的可消除全量副本

文件 worker 过去在解析后调用 `parsed.raw_text.strip()` 检查空正文，再由文本清洗依次构造换行规范化全文、完整行列表、清洗行列表和最终正文；切片服务即使已经持有非空 `document.cleaned_text`，仍会重新清洗 `raw_text`。PDF 解析还先保留所有页面的提取文本再统一拼接。图片 OCR 的请求路径则执行 `read_bytes()`、整份 Base64 编码和 JSON 序列化，使源文件字节、Base64 bytes、Base64 str 与最终请求体在一次合法图片处理期间叠加。上传上限能限制绝对值，但多个并发 worker 会放大这些可消除副本；决策 114 的并发限制不能替代单任务内存治理。

文本清洗现在使用 CR/LF 正则扫描原字符串，每次只切出当前行、折叠水平空白并写入 `StringIO`；一个 `pending_blank_line` 状态保留原有“连续空行折叠为一个空行”的语义，不再创建三份全文级中间集合。切片服务对已有非空清洗正文直接复用。PDF 解析按页把非空文本增量写入最终缓冲区并保持原页码及三换行分隔格式；worker 使用 `not raw_text or raw_text.isspace()` 拒绝空正文，不再为大字符串生成 `strip()` 副本。数据库继续同时保存业务需要的原文和清洗正文，本决策只移除可避免的中间对象。

OpenAI-compatible OCR 先把不含图片数据的请求序列化为固定 JSON 前后缀，再以 57 KiB 原始文件块读取图片。该大小是 3 的倍数，每块可以独立 Base64 编码并直接顺序拼接；服务按文件大小计算精确编码长度，加上前后缀后显式发送 `Content-Length`，因此不依赖 chunked transfer，也不物化完整图片、Base64 文本或 JSON body。语音转写原本已经把打开的文件对象交给 HTTPX multipart 编码器，继续沿用该流式边界。

回归测试锁定文本清洗的 CR、LF、连续空行和水平空白语义，限制大输入峰值，验证 PDF 不需要页面文本列表、已有清洗正文不会再次清洗、空正文检查不调用 `strip()`，并断言 OCR 不调用 `Path.read_bytes()`、按有界块编码且声明长度等于实际请求体。20,000 组随机 CR/LF/空白语料的新旧清洗结果完全一致；4.2M 字符探针的 tracemalloc 峰值从约 30.7 MiB 降至约 8.5 MiB，为旧实现的 27.7%。真实本地 HTTPX 服务接收 260,000 字节图片时得到 347,159 字节 JSON、`Content-Length=347159`、无 `Transfer-Encoding`，按 8 KiB 增量读取后 Base64 可完整还原原图。完整后端 476 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 118：外部 AI Provider 响应必须在 JSON 解析前实施解压后字节上限

OpenAI-compatible LLM、Embedding、OCR 和语音转写过去都使用同步 `httpx.post()`，该便利接口在返回 `Response` 前已经把上游正文完整读入内存。Embedding 的批量与维度校验、LLM/OCR/语音的业务字段读取都发生在 `response.json()` 之后，因此输入上下文、文件大小、Provider 批次和 worker 并发上限无法约束异常响应。配置错误、失控兼容端点或恶意上游可以返回无长度的无限 chunked 流，也可以用很小的 gzip 传输体解压成巨大 JSON；仅检查 `Content-Length` 既无法覆盖前者，也会把压缩长度误当成真实解析成本。多个普通与恢复 worker 并行时，这种响应会在任何业务契约生效前叠加到进程内存。

所有五个出站调用点现在统一使用 `post_json_limited()`：LLM 回答、LLM 整理、Embedding、OCR 和语音转写都通过 `httpx.stream()` 获取响应。helper 先执行 `raise_for_status()`，HTTP 错误保持既有异常语义且不下载错误正文；成功响应若声明的传输 `Content-Length` 已超限会立即关闭。随后以固定 64 KiB 调用 `iter_bytes()`，HTTPX 在这里已经完成 content encoding 解压，因此无长度分块、声明偏小和 gzip 膨胀都按实际待解析字节累计；越过边界的当前块不写入缓冲，连接由上下文管理器关闭，只有完整正文在限制内时才调用 JSON 解析。异常类型是内部 `RuntimeError`，不会被路由误映射成可公开的用户输入错误。

共享配置 `AI_PROVIDER_MAX_RESPONSE_SIZE_BYTES` 默认 8 MiB，可配置范围为 64 KiB 到 64 MiB；它不改变模型索引身份，也不需要触发 Embedding 重建。当前值通过 `/api/health/capabilities` 的 `ai_provider.max_response_size_bytes` 暴露，便于部署核对，但不把上限大小本身作为 readiness 成败条件。限制同时约束已声明的线上传输长度和解压后 JSON 字节：前者提供无需读正文的快速拒绝，后者提供最终内存边界。JSON 对象本身仍必须在上限内完整解析，这是当前非流式 OpenAI-compatible 响应契约的必要结果，而不再允许任意大的原始响应先进入解析器。

测试验证合法 JSON 按 64 KiB 读取、声明 65 字节而上限 64 字节时零正文读取、无长度响应在 `32 + 33` 字节越界块处停止、gzip 压缩长度小于上限但解压后超限时拒绝并关闭响应，以及非法上限在网络调用前失败；参数化调用还逐一证明五个 Provider 入口都读取共享配置。真实本地 HTTP 服务在上限 65,536 字节时发送总计 1,048,588 字节的 chunked JSON，客户端抛出 `ProviderResponseTooLargeError` 并在服务端只发送 139,264 字节时提前关闭连接；另一响应线上 gzip 仅 2,082 字节、解压后 2,097,164 字节，同样在 JSON 解析前被拒绝。完整后端 488 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 119：前台请求与后台任务必须共享外部 AI Provider 并发上限

决策 114 只统一了普通 BackgroundTasks 与恢复任务的 worker 数量。同步聊天一次可以先调用 Embedding 再调用 LLM，单篇与多资料整理调用 LLM，相关资料检索调用 Embedding；这些认证 API 在 AnyIO 路由线程池中执行，不占 job worker permit。它们可以与最多 50 个后台解析、富化和索引 worker 叠加，实际 OpenAI-compatible 请求并发由两个线程容量域和流量共同决定。决策 118 限制单个响应大小，但不能约束同时存在多少个请求、TLS 连接、响应缓冲和计费调用；一个合法账号发起大量并行请求时仍可能耗尽本机资源或上游配额。

共享 `post_json_limited()` 入口现在在打开 HTTP 流之前先从进程级 `ProviderRequestLimiter` 取得 permit，因此 LLM 回答、LLM 整理、Embedding、OCR 和语音转写的所有外部调用自动进入同一容量域，本地 extractive/hash Provider 不占槽位。限制器使用线程条件变量和显式 ticket 队列；只有队首且存在容量时才能增加 active，释放时唤醒等待者重新检查，稳定保持到达顺序并避免持续后台流量让旧请求饥饿。等待期间尚未创建 Provider 连接；调用方既有的聊天、整理、Embedding 批次和 worker 事务释放边界保持不变，不会为了等待 permit 新增长数据库事务。

permit 包围 HTTP 建连、状态处理、响应流读取和 JSON 解析，并由外层 `finally` 释放；正常返回、HTTP 错误、网络异常、响应越界和 JSON 错误都归还容量。响应上下文仍先关闭，再释放 permit，后续请求不会在前一个连接资源尚未清理时进入。配置 `AI_PROVIDER_MAX_CONCURRENT_REQUESTS` 默认 8、范围 1–100，在进程启动时构造 limiter；修改后必须重启。多 Uvicorn worker 或多实例的全局并发是各进程上限之和，部署必须按实例数与 Provider 配额折算。readiness 和 capabilities 同时暴露 max、active 与 waiting，容量占满本身不代表服务故障，因此不让 readiness 自动降级。

测试用 6 个真实线程和限制 2 阻塞响应流，稳定观测 `active=2`、`waiting=4`，只有两个线程进入 HTTP，释放后六项全部完成且峰值严格为 2；独立测试按确定的 0/1/2 到达顺序验证 FIFO，并证明响应读取异常后 active/waiting 归零、下一次调用可继续取得槽位，非法构造值和配置范围也在使用前拒绝。真实本地 ThreadingHTTPServer 接收 6 个请求时记录服务端峰值恰好为 2、完成数为 6，客户端 waiting 峰值为 4，最终 active/waiting 均为 0。完整后端 497 项、compileall 和 Alembic check 通过；不修改数据库结构。

## 决策 120：存储审计必须流式比对并将诊断限制为有界样本

决策 82 的只读审计过去先把当前 scope 的全部资料 key 和删除 outbox key 分别转成去重 tuple，再把 local 文件树或全部 S3 paginator page 合成完整 inventory list；随后又构造期望 key set、inventory set、orphan set 和四类完整诊断 tuple。对象总数、引用总数和 drift 数都没有上限，一个大 bucket 会让显式运维命令在输出前保留多份全量字符串集合。决策 83 的单 key dry-run 与 enqueue 还会为一个目标先执行同一完整审计，只为判断 key 是否出现在 orphan tuple；这既使精确操作随整个命名空间增长，也让以后限制诊断输出时无法安全判断未进入样本的目标。

完整审计现在按文档和删除任务 UUID 主键执行 keyset，每批默认只读取 500 个轻量 `id/key`，复制结果后立即 rollback，再处理下一批；不会使用 OFFSET、完整 ORM 或跨存储调用的数据库事务。去重后的 referenced/pending 标志写入系统临时目录中的 SQLite `WITHOUT ROWID` 主键表，关闭 journal、使用文件 temp store 并把 page cache 限为 2 MiB；临时磁盘随唯一期望 key 数增长，正常退出前显式 close 并删除。local 使用 `rglob` 生成器逐文件产出，S3 逐 paginator page 产出，inventory 每个 key 只对磁盘索引做一次点查，不再构造完整 bucket list。

结果继续为 referenced、pending、inventory、missing、orphan 和 invalid 返回精确计数，但四类 key 诊断只保留字典序最小的稳定样本；`STORAGE_AUDIT_SAMPLE_LIMIT` 默认 100、范围 0–10000，`diagnostics_truncated` 逐类说明计数是否超过已展示样本。数据库批次由 `STORAGE_AUDIT_BATCH_SIZE` 配置，默认 500、范围 1–10000。样本不是删除授权或完整处置清单。20,000 个逆序 inventory key 的测试仍精确报告 20,000 个 orphan，只保留前 5 个样本，tracemalloc 峰值低于 5 MiB；数据库 duplicate key 由磁盘主键合并，四类计数和样本截断分别测试。

单 key dry-run/enqueue 改为独立精确复核：先确认当前受管 prefix、key 合法、对象实际存在，再用一个包含资料引用与 pending outbox 两个 `EXISTS` 的 SQL 判断是否已受保护，不枚举 inventory。迁移 `0028_storage_audit_lookup` 使用 `CREATE INDEX CONCURRENTLY` 建立 `md5(file_path)` 部分表达式索引，避免超长 Text 直接进入 B-tree；查询先按 hash 定位候选，仍用完整 file_path、backend 和 scope 等值复核，碰撞不会误判。真实 catalog 显示索引 ready/valid/live，禁用顺序扫描后计划为 `Index Scan using ix_documents_file_path_md5`。现有跨数据库/存储非原子窗口与低写入时段复核要求保持不变。

真实 PostgreSQL 提交 5 条受控 indexed 资料，以 `batch_size=2` 审计时文档查询严格为 `2/2/1/0` 四批，5 次文件存在性回调均无活动 Session 事务且脚本连接池 checked-out 为 0；按 ID 清理后探针资料为 0、jobs 为 0。当前 local scope 的真实只读审计精确报告 1 个历史 orphan；受保护 key dry-run 返回 `orphan/action=none/0`，不存在 key 返回 `not_orphan/action=none/1`，两次调用前后 SHA256 不变且 outbox 仍为空。完整后端 511 项、compileall 和 Alembic check 通过；数据库版本升级为 `0028_storage_audit_lookup`。

## 决策 121：资料列表必须在 SQL 层排除正文并限制预览宽度

资料页码接口和 scan 接口的响应模型已经是 `DocumentListItem`，不包含原文、清洗正文、metadata 或存储位置，但 service 仍执行 `select(Document)`。FastAPI 的 response_model 过滤发生在 SQL、驱动和 ORM 加载之后，不能撤销完整行已经通过 PostgreSQL 连接传输并进入 Session identity map 的成本。文件上传上限为 25 MiB，数据库还同时保存 raw_text 与 cleaned_text；一次最多 100 行的合法列表请求因此可能在只显示标题和两行摘要时加载 GiB 级正文。summary 与 error_message 是 Text，若只排除正文但仍完整选择这两列，Provider 合法上限内的大输出仍会让行宽随内容增长。

Document 增加两个非持久化 `query_expression`：`summary_preview` 和 `error_message_preview`。列表与 scan 共用 `_document_list_statement()`，通过 `load_only(..., raiseload=True)` 只加载 id、title、source_type、status、created_at、updated_at，并以 PostgreSQL `left(column, 500)` 计算两个预览。raw_text、cleaned_text、metadata、user/storage/file 字段以及原始 summary/error_message 都不进入 SELECT；raiseload 让未来误访问排除列立即失败，不能退化成每行一次隐式懒加载。标签继续按当前最多 100 个 document ID 单次关联查询并附加，identity map 只保留有界数量的窄 ORM 对象。

`DocumentListItem` 通过 validation alias 从两个内部预览属性读取，公开 JSON 字段仍叫 `summary` 与 `error_message`，各自 schema 上限为 500；现有 Flutter 模型和卡片无需改动。关键词筛选仍可在数据库中的 title/raw/cleaned/summary trigram 预筛与字段 OR 中匹配完整内容，WHERE 引用大列不等于把它们放入 SELECT。单资料 `GET /documents/{id}` 继续使用完整 Document，Flutter 详情页本来就通过 `documentDetailProvider(id)` 独立请求，因此列表预览不会截断详情、编辑、整理或引用定位。

测试编译列表 SELECT，逐项拒绝 user、文件、存储、raw、cleaned 和 metadata 列，要求两个 `left(..., 500)` 及六个轻量字段，并验证 preview alias 只以公开字段名序列化、超过 500 在 DTO 边界失败；原搜索、标签 owner、页码稳定顺序、游标 lookahead 和标签附件测试全部保持通过。真实 PostgreSQL 提交一条含 2,000,000 字符 raw、2,000,000 字符 cleaned、1,000,000 字符 metadata blob 与各 2,000 字符 summary/error 的受控资料：列表 SELECT 不含三类大列，两个预览均为 500，raw 访问触发 raiseload，Pydantic 序列化增加 0 条 SQL，tracemalloc 峰值为 367,365 字节；独立详情查询仍返回全部五个原始长度。重启后的真实认证 API 列表与详情均返回 200；列表只有 9 个公开轻量字段、两个预览为 500 且没有 raw/cleaned，详情保留 600 字符原值和正文。两组探针按 ID 清理后不存在、jobs 为 0、连接池 checked-out 为 0。完整后端 515 项、compileall 和 Alembic check 通过；数据库结构仍为 `0028_storage_audit_lookup`。

## 决策 122：可持久化的模型文本必须有业务上限，消息读取必须兼容历史宽行

决策 118 把任意 Provider HTTP 响应限制为解压后 8 MiB，但传输上限不是业务字段契约。OpenAI-compatible 聊天回答仍可以把接近该边界的单个字符串直接写入 `messages.content`；一次消息页最多返回 100 行，合法历史请求因而仍可能传输和物化数百 MiB。整理结果在 `save_as_note=true` 时直到 `NoteCreate` 构造才碰到 200,000 字符输入上限，不保存时则可以直接返回 8 MiB；自动富化摘要完全没有字段上限。最近上下文虽然在组装 Provider 请求时切到 2,000 字符，数据库和 ORM 已经先加载了完整历史正文。单独给响应 schema 添加 `max_length` 会让旧宽行在序列化阶段返回 500，也不能阻止服务在此之前已经写入超大值。

业务层现在在 Provider 返回后、任何数据库写入前执行字符数校验：聊天回答最多 32,000，整理结果沿用笔记正文契约的 200,000，资料摘要最多 20,000，标签生成原始文本最多 4,000。聊天先验证回答再生成建议问题，整理先验证再决定是否保存，富化先验证摘要再请求标签；越界不会产生新会话、单边消息、AI 笔记或部分摘要。聊天与整理只捕获命名的 `ProviderOutputTooLargeError`，统一返回稳定 `502` 和“模型返回内容过长，请缩小问题或资料范围后重试”，内部长度诊断不进入公开响应；富化沿用已审核的后台错误包装。新内容不能无提示截断，精确等于上限仍可通过。

Message 增加非持久化的 `content_preview` 与 `content_truncated` 表达式。页码和 keyset scan 共用窄行语句，只加载 id、conversation_id、role、citations、created_at，以 `left(content, 32000)` 返回正文并用 `length(content) > 32000` 标记旧宽行；原始 content、user_id 和 metadata 不进入 SELECT，raiseload 阻止未来隐式补取。`MessageRead` 通过 alias 继续公开字段 `content`，同时新增 `content_truncated`；Flutter 在历史详情及继续会话后明确显示“仅显示前 32000 个字符”。最近六条模型上下文改为只选择 `role + left(content, 2000)`，不再构造完整 Message ORM。数据库中旧正文不迁移、不改写，只有读取表现有界且可见。

测试覆盖四个业务精确边界、超一字符、聊天建议调用顺序、整理保存前失败、富化摘要失败后不再请求标签、两条同步路由的稳定 `502`，并让真实 `OpenAICompatibleLLMProvider` 解析一份低于传输上限但高于聊天字段上限的响应，验证零 add/commit。SQL 投影测试要求两个内容表达式和五个轻量列、排除 user/metadata，并验证 DTO alias 与超限防线。真实 PostgreSQL 写入一条 2,000,000 字符历史助手消息：scan 返回 32,000 且 `content_truncated=true`，上下文返回 2,000，访问原 content 触发 raiseload，Pydantic 序列化新增 SQL 为 0，tracemalloc 峰值为 300,884 字节。探针会话按 UUID 级联清理后会话和消息均为 0。完整后端 530 项通过，Flutter analyze 零问题且聊天相关测试通过；不修改数据库结构。

## 决策 123：会话详情必须从最近页按需向前加载，并限制客户端历史窗口

决策 122 限制了单条消息和每页行宽，但 Flutter `ChatApi.listMessages()` 仍从正序 scan 的开头循环到 `next_cursor=null`，再一次把完整会话列表交给页面。打开会话详情会自动请求全部历史，消息数量没有业务上限；即使每条最多返回 32,000 字符，网络请求数、JSON 解码对象和 Dart 列表仍随整个会话增长。只把 scan 页大小从 100 调小会增加往返次数而不改变最终内存；只截取正序第一页又会展示最旧消息，无法自然继续当前会话。

后端保留原 `/messages/scan` 正序完整遍历契约，新增 `/messages/recent`。新端点使用独立 `chat.messages.created-id.desc` 游标，SQL 按 `(created_at, id) DESC` 和可选 `< cursor` 读取 `page_size + 1`，默认页大小 50；下一游标取当前降序页最旧一条，再把页内项目反转成正序响应。这样首个请求直接得到最近 50 条，更早页可稳定前插，原正序与新降序游标因 kind 不同不能交叉复用。查询继续复用决策 122 的窄行投影和既有 `(conversation_id, user_id, created_at, id)` 索引，不新增表或索引。

Flutter 的 `MessageHistoryPage` 保留 `items + nextCursor`，provider 首次只发一个 recent 请求，不再在 API 客户端内部循环。详情页只有用户点击“加载更早消息”才请求下一页，按消息 ID 去重并前插；本地窗口最多保留 200 条。继续向前超过窗口时保留正在浏览的较旧 200 条、丢弃较新端，并在顶部显示“返回最近消息”；继续提问若当前窗口已偏离最新位置，会先重新获取最近页再恢复聊天，不能把旧窗口误作当前界面。刷新同样回到最近页。加载中、较早页失败重试、无更早页和返回最新都有独立可见状态。

后端测试锁定降序 tuple 条件、唯一倒序 SQL、一行 lookahead、页内正序、游标指向最旧项目以及两种端点游标隔离。Flutter API 测试证明首屏只有一次 50 条请求，第二页只在显式 cursor 下请求；组件用 250 条五页数据验证请求游标顺序、200 条窗口和返回最近入口。真实 PostgreSQL 写入 121 条有序消息并走实际路由，三页严格为 `50/50/21`，边界为 `071..120`、`021..070`、`000..020`；按客户端前插后 121 个 ID 全部唯一且严格恢复 `000..120`，单页探针峰值 542,418 字节。重启后再创建 5 分钟临时认证会话，通过真实 HTTP 请求 51 条消息得到 `200 + 200` 和 `50/1` 两页，cursor 为 `true/false`，所有项目均包含截断标志。三次探针会话和临时认证记录均按 UUID 清理。完整后端 532 项、Flutter 129 项、analyze、compileall 和 Alembic check 全部通过；数据库仍为 `0028_storage_audit_lookup`。

## 决策 124：实时聊天状态必须与历史详情共享有界消息窗口

决策 123 只约束从历史详情加载的列表。用户留在提问页连续交互时，`ChatController.ask()` 仍把每轮 user/assistant 两个对象永久追加到 `ChatState.messages`；每条助手回答允许 32,000 字符，一个长时间不清空的合法会话会让 Flutter 状态、ListView 数据源和后续每次 spread 复制持续增长。历史详情即使只传入最近 200 条，继续提问后也会重新进入无界追加。后端最近六条上下文和 keyset API 已经有界，因此这一风险只需要治理客户端展示状态，不能通过删除数据库历史来掩盖。

## 决策 127：检索候选必须使用有界标量投影并严格限制上下文总长

## 决策 129：任务公开文本必须同时限制持久化宽度和历史读取宽度

## 决策 131：大资料详情正文必须按字符窗口加载并保持引用 offset 全局语义

决策 130 已经把资料详情从两份正文收敛为一份 canonical `content`，但该正文仍会一次性完整传输。合法上传文件可达 25 MiB，历史资料还可能更宽；服务端查询、JSON 编码、Dio 解码、Dart 模型和 Text 渲染会同时持有大字符串。引用的 `start_offset/end_offset` 是相对完整 canonical 正文的全局位置，直接截断首屏又会让深层引用无法定位，因此详情读取必须同时解决传输上限和 offset 语义。

`GET /documents/{document_id}` 现在接受 `content_offset` 与 `content_limit`，单窗上限固定为 50,000 字符，offset 请求上限为 100,000,000。详情投影在 PostgreSQL 中对既有 canonical 表达式执行 `substr(content, offset + 1, limit)`，并以 `char_length` 返回 `content_length`；响应新增实际请求的 `content_offset` 和表示当前窗口之后仍有正文的 `content_truncated`。完整 canonical 正文不进入 Python，摘要、错误和内部字段边界保持不变。同步创建笔记的内存响应走相同切片协议，`DocumentRead` 再以 50,000 字符 schema 上限阻止内部调用绕过响应边界。

Flutter 详情 provider 改为 `(id, contentOffset)` 查询键，普通入口从 0 加载，引用深链接从 `max(highlightStart - 5000, 0)` 直接加载目标附近窗口。页面显示当前字符范围并提供上一段、下一段图标操作；全局引用 offset 减去响应窗口 offset 后才传给正文高亮，窗口或引用变化时重置自动滚动状态。这样无需顺序下载前文即可定位深层引用，切换窗口也不会把局部下标误当成全局下标。旧离线数据缺少分页字段时继续按 `0/0/false` 解析。

测试覆盖 SQL `substr/char_length`、首窗/末窗/越界窗、DTO 超窗拒绝、Dio 查询参数、深层引用直接请求正确窗口以及前后窗口切换。真实 PostgreSQL 写入 2,000,000 字符 canonical 正文：首窗和中窗均严格为 50,000，末窗为 25,000，越界窗为空且 `content_truncated=false`；四次读取的 Session identity map 为 0，tracemalloc 峰值为 427,292 字节。探针按精确 UUID 清理且连接池 checked-out 为 0。完整后端 555 项、Flutter 138 项、analyze、compileall 和 Alembic check 通过；数据库结构仍为 `0028_storage_audit_lookup`。

## 决策 132：会话非详情工作流必须使用窄投影和数据库级联

会话目录过去通过完整 `Conversation` ORM 返回 `scope` JSONB，但历史页和首页最近会话只展示标题与更新时间；每页最多 100 项仍会解码并传输所有资料 ID、标签和来源范围，历史异常 scope 没有数据库宽度约束。三种消息分页入口为了确认 owner 也会先加载完整会话。重命名先加载再 refresh 全行，继续会话落库在已经得到规范化 `PreparedConversation.scope` 后又读取旧 scope。删除则调用 `db.delete(conversation)`，ORM 的 `delete-orphan` 关系可能在已有 `ON DELETE CASCADE` 的情况下物化全部消息正文、引用和 metadata。

目录改为不可变 `ConversationListItemView` 标量投影，只选择 `id/title/created_at/updated_at`；公开列表 schema 同步拆出不含 scope 的 `ConversationListItem`。单会话详情继续返回 scope，继续聊天的产品契约不变。Flutter 的 `ConversationSummary` 原本已把缺失 scope 解析为空范围，且目录卡片只使用标题与时间，因此无需额外请求或界面分支。count 与关键词过滤直接作用于会话表，不再从完整行子查询计数。

消息页、正序 scan 和 recent scan 共用 owner + conversation ID 的单列存在性查询。已有会话准备只加载 `id/title/scope` 并对其余属性启用 raiseload；持久化阶段使用 `SELECT id FOR UPDATE` 保留删除竞态防护，再集合化 UPDATE 已规范化 scope 与更新时间，不重新读取旧 JSONB。重命名使用 `UPDATE ... RETURNING id`，删除使用 `DELETE ... RETURNING id`；消息由外键级联删除，不触发 ORM 关系遍历。所有写入仍在原事务边界内提交。

测试锁定目录四列投影、公开响应不含 scope、消息归属单列查询、重命名/删除集合化 SQL、已有会话只锁 ID 及 Flutter 缺省 scope 兼容。真实 PostgreSQL 写入一份含 2,000,000 字符 legacy scope 的会话和 20 条各含宽正文与 metadata 的消息：目录读取 identity map 为 0、峰值 121,761 字节；最近消息读取只返回 32,000 字符正文预览且 Session 中无 Conversation ORM；集合化删除 identity map 为 0、峰值 99,009 字节，会话和 20 条消息均归零。探针按精确 UUID 清理且连接池 checked-out 为 0。完整后端 560 项、Flutter 139 项、analyze、compileall 和 Alembic check 通过；数据库结构仍为 `0028_storage_audit_lookup`。

## 决策 133：历史消息引用必须使用结构化有界投影

决策 109 和 129 已把聊天回答写入、消息正文读取和模型历史上下文设为有界，但消息列表仍直接选择完整 `citations` JSONB。正常检索最多生成 8 条引用，且引用预览通常很短；数据库列本身却没有数组数量或对象字段宽度约束。一个历史异常引用可以在正文限制之外携带任意大的标题、正文、章节和额外键，每页最多 100 条的行数限制无法约束 JSONB 解码、网络传输和 Flutter 对象分配。`MessageRead.citations` 过去还是无结构的 `list`，响应序列化不会执行 `Citation` 字段契约。

Message 新增非持久化 `citations_preview` 表达式，历史列表不再 load 原 citations。SQL 先用 `jsonb_typeof` 把非数组值降为空数组，再通过 `jsonb_array_elements ... WITH ORDINALITY` 按原顺序读取对象并在数据库中 `LIMIT 8`。每项使用 `jsonb_build_object` 只重建 11 个公开字段：UUID 截到 36 字符，标题和章节截到 255，引用正文截到 223，来源截到 32，数值文本截到 32；最后按 ordinality 聚合为 JSONB 数组。原始对象的额外键、后续项和宽字段不会进入 Message ORM，访问持久 citations 会触发 raiseload。

`Citation` schema 现在限制标题、正文、章节、非负索引与 offset、正页码和有限浮点数；实时响应与历史列表都最多 8 项。历史投影中的 UUID、枚举或数值若仍非法，`MessageRead` 在固定 8 项内逐项验证并丢弃该项，不让单条旧脏数据导致整页 500。回合持久化在 add 前再次用同一 Citation schema 规范化并裁到 8 项，因此即使未来检索调用方改变，也不能把更宽结构写入新消息。

测试锁定 JSONB LATERAL 分解、字段重建、顺序聚合、8 项 limit、各字符串边界、原列非直接投影、非法历史项丢弃及 9 条新引用只写 8 条。真实 PostgreSQL 写入一条 `citations` 为 6,003,338 字节的历史消息，其中首项三个字段各 2,000,000 字符、第二项 UUID 非法、总计 12 项：SQL 返回前 8 项，schema 公开 7 项，首项标题/正文/章节严格为 `255/223/255`，原 citations 访问触发 raiseload，Session identity map 仅含当前 Message，tracemalloc 峰值 505,155 字节。探针消息与会话按精确 UUID 清理且连接池 checked-out 为 0。完整后端 563 项、Flutter 139 项、analyze、compileall 和 Alembic check 通过；数据库结构仍为 `0028_storage_audit_lookup`。

## 决策 134：会话详情与继续提问必须读取结构化有界 scope

决策 132 已从会话目录、消息归属检查和删除路径移除 scope，但单会话详情与继续提问仍会先读取完整 `Conversation.scope` JSONB，再由 Pydantic 或 `_bounded_legacy_scope()` 校验。新请求固定限制为最多 100 个资料、20 个标签和 7 个来源类型，数据库列却允许历史额外键、超量数组、超宽字符串及非法 UUID/枚举。应用层事后切片不能阻止原始 JSONB 在 PostgreSQL 驱动和 ORM 中完整解码；深历史会话打开或继续时仍可能产生无界请求内存。

Conversation 新增非持久化 `scope_preview`。详情语句只加载 `id/title/created_at/updated_at`，原 scope 使用 raiseload；三个公开数组分别通过相关 LATERAL 子查询处理。SQL 先确认目标键是数组，再用 `jsonb_array_elements ... WITH ORDINALITY` 过滤字符串并保持顺序；资料、标签和来源分别在数据库中限制为 `100/20/7` 项，元素分别截到 `36/64/32` 字符，再聚合进只含 `document_ids/tags/source_types` 的新 JSONB 对象。额外键、后续元素和宽字符串不会进入 Conversation ORM。

`ConversationRead.scope` 从松散 dict 收紧为 `ChatScope`，但公开 JSON 字段名和三个数组保持不变。共享 legacy 规范化函数对 SQL 已限宽的候选逐项解析：丢弃非法 UUID 和来源枚举、清理空标签并再次执行数量边界。详情响应、重命名后的响应和 `_prepare_conversation()` 共用同一详情投影；继续提问得到规范化 `PreparedConversation.scope` 后，仍按决策 132 的 ID 行锁与集合化 UPDATE 写回，不需要重新读取原 JSONB。Flutter 模型继续按既有 scope 结构解析，无客户端分支。

测试锁定三组 JSONB LATERAL 分解、WITH ORDINALITY、`100/20/7` 数量上限、`36/64/32` 字符上限、原 scope 非直接投影和 schema 脏值过滤。真实 PostgreSQL 写入一份 `scope` 为 4,004,420 字节的历史会话，包含 2,000,000 字符额外 blob、2,000,000 字符标签、超量数组与非法 UUID/来源：详情公开 `99/20/5` 个合法资料、标签和来源，首标签严格为 64 字符，原 scope 访问触发 raiseload，tracemalloc 峰值 435,389 字节；继续提问准备返回同一规范化范围，峰值 284,663 字节。探针会话按精确 UUID 清理且连接池 checked-out 为 0。完整后端 565 项、Flutter 139 项、analyze、compileall 和 Alembic check 通过；数据库结构仍为 `0028_storage_audit_lookup`。

## 决策 135：认证高频路径必须使用有界用户公开资料投影

`users.avatar_url` 是无长度约束的 Text，`UserRead` 过去也没有公开上限。登录、改密和 `/auth/me` 都通过完整 User ORM 读取头像；一个历史异常头像会在 Argon2 校验、会话签发或“我的”页面响应之前完整进入 Python。重复注册只需判断邮箱是否存在却加载整行，账号删除只需 ID、邮箱与密码哈希却同时加载姓名、头像和时间字段。虽然当前产品没有头像更新接口，数据库恢复、旧版本或人工数据仍可能形成宽值；缺少写入口不能替代读取边界。

公开头像边界固定为 2,048 字符，`UserRead` 同时声明邮箱 255、姓名 128 和头像 2,048 的 schema 上限。User 新增非持久化 `avatar_url_preview`；公开用户语句只加载 `id/email/name/created_at` 并用 SQL `left(avatar_url, 2048)` 返回头像，不选择密码哈希，原 avatar 使用 raiseload。`/auth/me` 改用该投影并立即转换成独立 UserRead，因此返回后不会持有 ORM。

登录和改密继续使用 User ORM，以保留密码验证、必要的 Argon2 重哈希与用户行锁，但认证语句只额外加载 `password_hash`，头像仍走同一 SQL preview。账号删除的锁行语句进一步缩到 `id/email/password_hash`，不选择姓名、头像或时间；现有数据归属检查、批量删除和 outbox 事务不变。重复注册检查改为只选择 User ID。新注册用户头像固定为空；内存兼容转换仍会把非投影的旧调用方头像裁到相同边界。

测试锁定公开、认证和删除三类 SELECT 的精确字段，要求头像使用 `left`、公开查询排除密码、删除排除所有公开资料载荷，并验证 DTO 与内存转换的 2,048 边界。真实 PostgreSQL 写入头像为 2,000,000 字符的临时用户：公开查询返回 2,048，原头像与密码哈希均触发 raiseload，Session identity map 只有当前窄 User，tracemalloc 峰值 204,028 字节；真实登录返回同样的 2,048 字符，数据库原头像长度保持 2,000,000，包含 Argon2 校验和令牌签发的峰值为 1,311,555 字节。探针用户、会话与账号限流记录按精确标识清理且连接池 checked-out 为 0。完整后端 570 项、Flutter 139 项、analyze、compileall 和 Alembic check 通过；数据库结构仍为 `0028_storage_audit_lookup`。

## 决策 136：每个受保护请求的认证必须使用单查询窄投影

决策 135 收窄了登录、改密和 `/auth/me` 的用户查询，但 FastAPI 的 `authenticated_access` 仍在每个受保护请求上依次执行 `db.get(AuthSession, session_id)` 与 `db.get(User, user_id)`。第二次 ORM 主键查询会完整加载 User，包括无界历史头像；因此资料、聊天、任务、标签和设置等所有已经优化的接口，仍会在进入自身 service 前付出宽用户行解码成本。两次 ORM 查询还把 AuthSession 与 User 留在 identity map，而认证实际只需要确认 session 属于 token 用户、未过期且关联用户存在。

认证依赖现在执行一条标量行查询：从 `auth_sessions` 只选择 `expires_at`，按 token 的 session ID 与 user ID 同时过滤，并 JOIN users 证明关联用户仍存在。查询不选择 session 的 client name/created_at，也不选择 User 的邮箱、密码、姓名、头像或时间字段；结果是普通 Row，不创建任何 ORM。JWT 签名、issuer、audience、token type、subject、session ID 和时钟偏移仍先由既有解码器验证，数据库过期时间继续使用当前 UTC 时间判断。

测试覆盖缺失/非法/过期 token、缺失 session、跨用户 session、缺失用户和有效访问原语义，并编译 SQL 要求只有 `auth_sessions.expires_at` 与 users JOIN、禁止全部用户公开/私有列及非必要 session 列。真实 PostgreSQL 为头像 2,000,000 字符的临时用户创建有效会话，在同一 Session 连续执行 100 次真实 token 验证：每次均返回精确 user/session ID，identity map 始终为 0，tracemalloc 峰值 184,507 字节，数据库头像长度保持 2,000,000。探针会话与用户按精确 UUID 清理且连接池 checked-out 为 0。完整后端 571 项、Flutter 139 项、analyze、compileall 和 Alembic check 通过；数据库结构仍为 `0028_storage_audit_lookup`。
